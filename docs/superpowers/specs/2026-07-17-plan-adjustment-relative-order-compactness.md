# 计划调整相对顺序稳定与紧凑排程设计

> Scope update 2026-07-20: 本轮只解决普通计划调整中的可避免排程空档。关键路径计算/展示、新等待原因诊断、API/Schema/数据库和前端改造不在本轮范围。

> Implementation 2026-07-20: `relative_order_compact_v1` 已落地。服务层从基线任务的具体资源、活动组、状态连续性组和已匹配子系统连续性责任组编译非重叠顺序对；Scheduler 依次锁定 makespan、范围外反转数、全部反转数和优先级加权开始时间，最后应用既有软目标。验证：调整专项 13 passed，相关 Scheduler/阻塞/API 回归 68 passed，后端全量 370 passed。

## 1. 问题与设计结论

现行普通调整先最小化范围外/全部活动的绝对开始时间变化数和变化分钟数，之后才处理 makespan 与排期软目标。这会把基线时间戳连同基线空档一起锁住：即使活动可以合法提前，求解器也会为了“少移动”保留空档。

新的稳定性语义如下：

- **工期优先**：硬约束可行后，先取得最小 makespan。
- **顺序稳定**：“少移动”只表示有业务意义的活动执行顺序尽量不反转，不表示开始时间戳尽量不变。
- **排程压紧**：在最小工期和最少顺序反转条件下，让活动尽量早开始，消除可避免空档。
- **并行不造序**：基线中原本重叠/并行，或彼此没有共同顺序来源的活动，不因稳定性目标被强制串行。

因此，绝对时间变化仍可在候选对比中展示，但不再进入优化表达式。

## 2. 约束语义边界

硬约束继续包括：

- Planner 推导的系统工艺依赖；
- 资源容量与互斥；
- 工作日历连续可用窗口；
- `not_before`、`finish_not_after`、`fixed_start`、`freeze`；
- 人工 `precedence`。

`precedence(A, B)` 的精确定义仍是：

```text
start(B) >= end(A)
```

它是“最小间隔为 0 的 Finish-to-Start”，不是“B 必须紧接 A”。如果 B 同时等待其他前序、资源、日历或固定时间，A 与 B 之间可以存在必要间隔。强制无等待相邻属于另一种约束，本票据不引入。

## 3. 词典优化阶段

设活动集合为 `T`，调整范围为 `S`，活动 `i` 的开始时间为 `s_i`，优先级权重沿用 `high=4 / normal=2 / low=1`。

### L0：硬约束可行

所有硬约束必须满足。无解时保持现有 assumption core 诊断，不创建候选计划。

### L1：最小工期

```text
minimize makespan
```

取得并锁定最优值 `M*`。这一步从最终加权目标中提升为独立词典阶段，连续性或稳定性目标不能用更长工期交换更低成本。

### L2：范围外顺序反转最少

对两个端点都在调整范围外的基线顺序对 `P_out`：

```text
minimize Σ inversion(a, b), (a, b) ∈ P_out
```

先保护范围外的执行顺序，允许其绝对时间整体前移或后移。

### L3：全部顺序反转最少

对全部基线顺序对 `P_all`：

```text
minimize Σ inversion(a, b), (a, b) ∈ P_all
```

其中基线关系为 `a` 在 `b` 前；候选中只有 `start(b) < start(a)` 才算反转。候选同一时刻开始不算反转，避免稳定性目标阻止合法并行化。

### L4：加权最早开始压紧

```text
minimize Σ weight(i) × start(i), i ∈ T
```

全部活动都进入该表达式；没有显式 `priority` 的活动按 `normal` 处理。该阶段在 `M*` 和顺序反转最优值已锁定的可行域内执行，因此：

- 不会为了左移而延长总工期；
- 不会为了左移而增加已锁定的顺序反转；
- 如果某活动可以在不移动其他活动的情况下提前至少 1 分钟，当前解就不可能是该阶段最优，因而可排除无依据的独立空档。

不采用“最小化前后活动 gap 总和”，因为在多前序汇合场景中，该目标可能通过把较早完成的前序向右推来缩小 gap，反而制造不紧凑排程。

### L5：既有软目标择优

在 L1-L4 的最优值全部锁定后，继续应用现有 ObjectiveRegistry 和注册排期规则的软成本。硬性排期规则仍在 L0 生效；软规则不能破坏最小工期、顺序稳定和左移压紧的既定最优值。

最终阶段中的 `minimize_makespan` 项可保留为兼容元数据，但因 `makespan == M*` 已锁定，不再改变解。

## 4. “有业务意义的顺序对”

不能把所有活动按步骤编号建立全局顺序，否则会把独立分支错误串行化。顺序对从基线实际排程和业务分组中生成。

### 4.1 顺序来源

第一阶段支持以下来源：

1. **基线具体资源时间线**：两个活动在基线分配到同一 `resource_id`，且时间不重叠；
2. **活动连续性组**：两个活动属于同一 `activity_group_id`，且基线时间不重叠；
3. **状态连续性组**：两个活动共享 `state_continuity_groups[].state_group_id`，且基线时间不重叠；
4. **注册 group-continuity 规则组**：由规则编译结果提供稳定的 group key，且基线时间不重叠。

系统工艺依赖已经是硬约束，不需要额外创建反转变量；它可保留为顺序来源诊断，但从软反转目标中去重。

### 4.2 建对规则

对同一顺序来源中的活动按 `(start_min, end_min, step_order)` 稳定排序。仅当 `end(a) <= start(b)` 时建立 `a → b`；基线有重叠或同时开始时不建立顺序。多个来源得到同一 `(a,b)` 时去重，并保留来源列表用于解释。

候选反转布尔量定义为：

```text
inv(a,b) = 1  <=>  start(b) + 1 <= start(a)
inv(a,b) = 0  <=>  start(b) >= start(a)
```

范围外顺序对要求两个端点都不在 `S`；边界对和范围内对只进入 L3。

### 4.3 规模控制

顺序对只在共享资源或共享业务组内产生并全局去重，不对全体活动做笛卡尔积。实现时记录每种来源的组数、pair 数和去重后总数；性能门禁若证明特定超大组产生不可接受的二次规模，再单独设计可配置的稀疏化策略，本设计不先用硬编码阈值改变语义。

## 5. 求解阶段与超时

每个词典阶段只有在 CP-SAT 返回 `OPTIMAL` 时，才能把该阶段最优值标记为“已证明”并作为严格设计承诺。

若某阶段只返回 `FEASIBLE`：

- 可以返回可行候选，但 `optimization_complete=false`；
- 诊断必须给出 `reached_stage`、该阶段状态和后续未证明阶段；
- UI 不得显示“已满足最小工期/已完成压紧”；
- 不得把一次可行值描述为数学最优值。

实现可以在剩余预算内锁定当前可行值继续改善后续目标，但所有后续结果都必须继承“未证明”的状态；验收场景必须取得全部关键阶段 `OPTIMAL`。

## 6. 数据与兼容性

### 6.1 内部上下文

`adjustment_context` 增加内部字段：

```text
optimization_policy: relative_order_compact_v1
base_ends: {step_order: end_min}
base_order_pairs: [{predecessor_step_order, successor_step_order, sources[]}]
```

这些字段按 `step_order` 编译，不把数据库瞬时 step id 带入 Scheduler。策略名随候选求解诊断/覆盖快照持久化，以便复现。

### 6.2 API 与历史计划

- 调整请求和六类约束 wire shape 不变；无需数据库迁移。
- 已确认历史计划和已生成候选保持不可变。
- 新建或重新试算的普通调整使用新策略；旧 `preview_ready` 被重新试算时应先废弃旧候选，再按新策略生成。
- `task_diffs.changed`、`shift_min`、范围内外变化数继续表示绝对时间差，只用于展示。

## 7. 本轮诊断边界

复用现有 `diagnostics.schedule.adjustment_optimization` 阶段列表，只将阶段类型替换为新的词典目标，并继续记录：

```text
type
solver_status
optimum
is_proven_optimal
locked
```

现有候选预览、绝对 `shift_min`、关键路径和等待原因输出保持不变。本轮不新增顺序反转摘要、左右浮时字段或前端展示。实现测试直接通过候选开始/结束时间、makespan 和阶段最优值验证空档压缩。

## 8. 用户场景预期

对“设置 6 号在 3 号前完成，15/16 与前后活动出现空档”的场景：

- 6→3 的人工关系先作为硬约束满足；
- 新候选先取得该硬约束下最小 makespan；
- 15、16 若在不增加顺序反转的条件下可提前，会被 L4 左移，不再保留基线绝对时间；
- 16→20 若 20 还必须等待另一前序、资源或日历，间隔可以保留，并在等待诊断中列出真正阻塞项；
- 任何残余间隔都不能再以“保持基线开始时间”为理由。

## 10. 验收矩阵

| 场景 | 必须证明 |
|---|---|
| 无额外约束、基线含可避免空档 | makespan 最优；活动左移；顺序反转为 0 |
| 人工反转两活动 | 新 precedence 满足；makespan 最优；仅必要顺序变化发生 |
| 两个独立并行活动 | 不建立保序对；并行能力不下降 |
| 同一具体资源的串行活动 | 在同 makespan 下优先保持基线资源时间线顺序 |
| 15/16 类非关键活动 | 无阻塞时左移；不因基线时间戳被钉住 |
| 多前序汇合 | 后项等待最晚前序；较早前序 gap 不被误报为可消除 |
| 日历/固定开始/冻结 | 必要空档保留且原因可解释 |
| priority high/normal/low | 不改变 makespan/顺序最优值，在压紧阶段体现尽早优先级 |
| 求解超时仅 FEASIBLE | 候选可用但明确标记未证明最优 |
| MI-HP-001 与调整全量回归 | 活动集合、工期、资源需求、系统依赖、规则硬约束均不回退 |

## 11. 不采用的方案

- **继续最小化绝对时间位移**：会保留基线空档，与新语义冲突。
- **只最小化 makespan**：能缩短总工期，但同工期解中仍可能存在内部漂移和空档。
- **最小化所有 predecessor gap**：可能通过右移较早前序来“缩小 gap”，并不等于左移压紧。
- **按 step_order 给所有活动建立顺序**：会给独立并行分支制造不存在的业务关系。
- **把 precedence 改成强制紧邻**：多前序、资源和日历场景下过强，且改变现有约束契约。
