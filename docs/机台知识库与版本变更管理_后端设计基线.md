## 2. 领域模型

### 2.1 核心概念

| 概念 | 定义 |
|---|---|
| 机台类型基线 | 某类机台可复用的能力、工艺、状态、活动、规则和资源需求模板 |
| 基线主线 | 机台类型唯一可移动引用 `baseline_main`，指向当前基线版本 |
| 机台实例 | 一台具体集成设备，属于一个机台类型 |
| 实例头版本 | 机台实例唯一可移动引用 `instance_head`，指向当前实例版本 |
| 冻结基线 | 实例版本明确记录的基线 Revision；基线主线后续变化不自动影响实例 |
| 完整实例模型 | 实例 Revision 的逻辑完整 Manifest，可独立恢复全部知识内容 |
| 知识版本 | 不可变 Revision，描述一次正式提交 |
| 运行时快照 | 求解当次的当前状态、目标状态、临时可用性等输入，不属于知识版本 |

### 2.2 MVP 拓扑

```text
MachineType
  └─ baseline_main ──> B3
                       ↑
                  B1 → B2 → B3

Machine
  ├─ instance_head ──> I4
  └─ I4.pinned_baseline_revision_id = B2
                  I1 → I2 → I3 → I4
```

MVP 约束：

- 每个机台类型只有一个 `baseline_main`；
- 每个机台实例只有一个 `instance_head`；
- 每条历史为单父线性历史；
- 不提供命名分支；
- 回写和升级内部使用三方合并，但不暴露通用分支模型；
- 实例头版本保存完整模型，不保存运行时“差异补丁栈”。

### 2.3 不可变规则

1. Revision 创建后不可修改、覆盖或删除。
2. Manifest 和 Content Object 创建后不可修改。
3. 可移动的只有 `knowledge_ref`。
4. “恢复历史”必须创建新 Revision，不能把引用直接退回。
5. 对象和关系身份与名称、编码、数据库自增 ID 解耦。
6. 关系端点或关系类型变化按删除旧关系、创建新关系处理。
7. 求解只读取正式实例 Revision，不读取前端草稿。
8. 知识版本和计划版本 `PlanFamily/CandidatePlan` 完全独立。

### 2.4 业务范围创建

`MachineType` 和 `Machine` 是知识版本的业务范围锚点。新建范围不能先留下一个可被求解读取、但没有首版本的半成品记录。

MVP 使用原子创建：

- 创建机台类型时，在同一事务中创建 `MachineType` 范围锚点、首个 Manifest、`B-000001` 和 `baseline_main`；
- 创建机台实例时，在同一事务中创建 `Machine` 范围锚点、完整实例 Manifest、`I-000001` 和 `instance_head`；
- 首版本验证失败时，范围锚点和版本均不落库；
- 前端首版本之前的多步录入只属于初始化草稿；
- 停用范围通过新的正式版本及兼容投影表达，MVP 不物理删除已有知识范围和历史版本。

## 3. 版本内容边界

### 3.1 进入知识版本

#### 基线和实例共同知识

- 状态包；
- 原子状态本体；
- 状态包成员引用；
- 活动包；
- 原子活动本体；
- 活动包原子活动引用；
- 原子活动工序规则；
- 规则前置、效果、时长和资源需求；
- 原子状态到原子活动的 `input` 关系；
- 原子活动到原子状态的 `output` 关系；
- 状态维度定义，包括基线定义以及实例新增或覆盖；
- 资源类型；
- 必要展示布局和引用布局。

#### 基线侧配置

- 机台类型配置；
- 工作日历模板引用；
- 默认排程配置。

#### 实例侧配置

- 机台实例配置；
- 具体机器资源；
- 默认工作日历及其修订引用；
- 状态维度日历映射；
- 实例排程配置。

### 3.2 不进入知识版本

- 当前状态快照；
- 目标状态快照；
- 过程状态快照；
- 临时资源可用性；
- 求解开始时间；
- 求解请求状态；
- 求解结果、候选计划和计划调整；
- Scope Guard 及其前置条件；
- 维护意图；
- 虚拟活动；
- 历史 `context_input`、`declared_output` 包级绑定。

历史废弃数据可留在旧表供审计，但不得进入新的 Manifest、有效模型或求解。

### 3.3 活动包边界

- 活动包只提供组织、分类、筛选和复用入口；
- `ActivityPackageAtomicRef` 只表达管理引用；
- 活动包名称、层级、排序和成员变化不得隐式改变求解模型；
- 如果用户按活动包筛选求解范围，API 层必须先解析成明确的 canonical 原子活动 ID 集合；
- 有效模型只读取 active 原子活动、规则和原子活动的输入/输出关系。

## 4. 稳定身份

### 4.1 标识定义

| 标识 | 类型 | 含义 |
|---|---|---|
| `entity_key` | UUID | 对象的跨版本稳定身份 |
| `relation_key` | UUID | 关系的跨版本稳定身份 |
| `revision_id` | UUID | 不可变知识版本身份 |
| `manifest_id` | UUID | 逻辑完整清单身份 |
| `content_hash` | `sha256:<64 hex>` | 规范内容地址 |
| `manifest_hash` | `sha256:<64 hex>` | 规范 Manifest 地址 |

`entity_key` 和 `relation_key` 在数据库中统一存入 `knowledge_identity.identity_key`，通过 `identity_kind` 区分。

### 4.2 身份规则

- 新对象或关系由客户端生成 UUID，并由服务端校验唯一性；这样同一草稿中新对象可以互相引用；
- 历史数据迁移使用固定命名空间 UUIDv5：`solver-legacy/<table>/<legacy-id>`，保证重跑稳定；
- 新建数据使用 UUIDv4；
- 修改 `name`、`code`、描述或布局不改变身份；
- 删除后重新创建语义相同对象仍获得新身份，除非执行的是明确的历史恢复；
- 数据库自增 ID 只作为兼容投影内部主键，不进入知识身份或内容哈希；
- 实例从基线继承的对象继续使用相同身份；
- 实例新增对象的 `origin_scope_kind` 为 `instance`。

### 4.3 关系身份

关系的以下字段属于身份语义：

- 关系类型；
- 起点对象；
- 终点对象；
- 输入/输出角色。

任一字段改变时：

```text
delete(old relation_key)
+ create(new relation_key)
```

关系的展示样式或布局变化可以保留同一 `relation_key`。

## 5. 规范内容与内容寻址

### 5.1 Canonical Envelope

每个内容对象使用：

```json
{
  "schema": "canonical-json/v1",
  "object_kind": "atomic_activity",
  "semantic": {},
  "presentation": {}
}
```

`semantic` 保存影响业务和求解的内容；`presentation` 保存布局、折叠状态等展示内容。

### 5.2 规范化规则

- 编码为 UTF-8；
- Unicode 字符串归一化为 NFC；
- JSON 对象键按 Unicode 码点升序；
- 数组保持业务顺序；只有在对象 Schema 明确声明为集合时，才按稳定身份排序；
- 布尔值只使用 `true/false`；
- 整数使用 JSON 十进制整数；
- Decimal 转为无指数、去除无意义尾零的字符串；
- 时间转为 UTC ISO-8601，格式 `YYYY-MM-DDTHH:mm:ss.ffffffZ`；
- 空值统一使用显式 `null`，不允许 NaN、Infinity 或未定义值；
- 不包含数据库自增 ID、创建时间、更新时间和操作者等非业务字段。

### 5.3 内容哈希

```text
content_hash = "sha256:" + SHA256(canonical_utf8_bytes)
```

相同 Canonical Envelope 必须得到相同哈希。数据库以 `content_hash` 为唯一键，因此相同内容只保存一次。

布局变化会产生新的内容对象，但差异和回写时归入 `presentation` 变化，默认不参与回写。

### 5.4 Manifest 哈希

Manifest Entry 规范排序键：

```text
(identity_kind, identity_key, object_kind, content_hash)
```

`manifest_hash` 对规范排序后的完整 Entry 数组计算 SHA-256。相同逻辑完整模型必须得到相同 `manifest_hash`。

## 6. Manifest 与 Revision

### 6.1 Manifest

Manifest 是某个知识版本的逻辑完整清单：

```text
identity_key → object_kind → content_hash
```

它不是差异文件。一个实例 Manifest 必须能够在不读取其冻结基线 Manifest 的情况下恢复完整实例知识。

### 6.2 未变化内容复用

提交时以当前头版本 Manifest 为基础：

- 新增或修改条目引用新 `content_hash`；
- 删除条目从新 Manifest 中移除；
- 未变化条目继续引用原 `content_hash`；
- 新 Manifest 仍是完整清单。

### 6.3 Revision

Revision 至少包含：

- 业务范围；
- 顺序版本号；
- 父 Revision；
- Manifest；
- 实例冻结基线；
- 提交说明；
- 结构和求解准备摘要；
- `ready/blocked` 状态；
- 创建时间和审计操作者。

基线显示号为 `B-000001`，实例显示号为 `I-000001`。显示号只用于人读，不作为外键。

### 6.4 版本状态

| 状态 | 含义 | 是否可求解 |
|---|---|---|
| `ready` | 结构有效，求解准备通过 | 是 |
| `blocked` | 结构有效，但存在求解阻断 | 否 |

结构无效的内容不得创建 Revision。

## 8. RevisionStore

### 8.1 权威边界

RevisionStore 是知识版本的唯一权威读写入口。现有规范化业务表在过渡期作为当前头版本的兼容投影。

调用关系必须符合：

```text
API → Service → RevisionStore / Domain → Persistence
```

Domain 不导入 FastAPI，API 不直接编排 Manifest 或合并算法。

### 8.2 接口

```python
load_revision(revision_id) -> KnowledgeModel
get_entry(revision_id, identity_key) -> KnowledgeEntry | None
commit(command) -> CommitResult
diff(from_revision_id, to_revision_id, options) -> DiffResult
dependency_closure(revision_id, selection) -> ClosureResult
merge(base_revision_id, ours_revision_id, theirs_revision_id, selection) -> MergeResult
verify(revision_id_or_manifest) -> VerificationResult
```

### 8.3 实现约束

- 上层调用者不得直接查询 Manifest Entry 拼装业务模型；
- 扁平 Manifest 的实现细节不得泄漏进 API Schema；
- 不可变 Revision 可以按 `revision_id` 缓存；
- 提交 Revision、移动 Ref 和更新规范化投影必须在同一数据库事务；
- 任一步失败整体回滚；
- 未来 Merkle Tree 只替换 RevisionStore 内部，不改变接口和业务语义。

## 9. 提交协议

### 9.1 提交命令

```json
{
  "expected_head_revision_id": "uuid-or-null-for-first-version",
  "idempotency_key": "uuid",
  "message": "增加真空联调状态转移",
  "allow_solver_blockers": false,
  "changes": [
    {
      "operation": "upsert",
      "identity_kind": "entity",
      "identity_key": "uuid",
      "object_kind": "atomic_state",
      "content": {
        "semantic": {},
        "presentation": {}
      }
    },
    {
      "operation": "delete",
      "identity_kind": "relation",
      "identity_key": "uuid",
      "object_kind": "activity_state_binding"
    }
  ]
}
```

所有新对象和关系必须携带 UUID，服务端不接受只用临时整数 ID 的跨对象引用。

### 9.2 提交流程

1. 锁定目标 `knowledge_ref`；
2. 比较 `expected_head_revision_id`；
3. 检查幂等键；
4. 加载当前完整 Manifest，首版本使用空 Manifest；
5. 校验身份归属和操作合法性；
6. 应用新增、修改和删除；
7. 生成规范内容并按哈希去重；
8. 生成完整新 Manifest；
9. 执行结构验证；
10. 执行模型健康和求解准备验证；
11. 结构错误则整体失败；
12. 有求解阻断且未允许则返回复核响应；
13. 创建不可变 Revision；
14. 移动 `baseline_main` 或 `instance_head`；
15. 更新规范化兼容投影；
16. 提交事务并返回新版本。

### 9.3 无变化

Manifest Hash 与当前头版本相同时拒绝提交，返回 `KNOWLEDGE_NO_CHANGES`，不创建空 Revision。

### 9.4 并发

若当前头版本与期望版本不同：

- 返回 HTTP 409；
- 返回当前头 Revision；
- 不应用任何变化；
- 不消费为成功幂等请求；
- 前端保留草稿并进入重新应用流程。

## 10. 差异与依赖闭包

### 10.1 差异单位

先按稳定身份比较 Manifest Entry：

- 只在目标存在：新增；
- 两侧存在且内容哈希不同：修改；
- 只在来源存在：删除。

修改项继续比较 Canonical Envelope 的顶层字段，分别报告：

- `semantic` 变化；
- `presentation` 变化。

### 10.2 关系差异

关系作为一等条目参与 Diff。端点变化不会成为字段修改，而是旧关系删除和新关系新增。

### 10.3 依赖闭包

选择性回写必须自动补齐：

- 新关系引用的起点和终点对象；
- 原子状态依赖的状态维度；
- 原子活动规则依赖的原子活动；
- 规则依赖的资源类型；
- 引用依赖的包和本体；
- 删除对象所必需的关系删除。

必要依赖在结果中标记 `dependency_reason`，调用者不得取消。

如果删除对象所需的依赖删除并不存在于实例变化中，返回 `KNOWLEDGE_DEPENDENCY_INCOMPLETE`，不得隐式删除基线中额外关系。

### 10.4 顶层字段选择

MVP 允许对修改项选择顶层字段。嵌套 JSON 和数组作为一个原子字段处理，不做数组元素级合并。

`presentation` 默认不选入回写。

## 11. 三方合并

### 11.1 统一规则

对每个身份和选中顶层字段：

1. Ours 等于 Base、Theirs 改变：采用 Theirs；
2. Theirs 等于 Base、Ours 改变：采用 Ours；
3. Ours 等于 Theirs：采用共同结果；
4. 两侧修改不同顶层字段：自动合并；
5. 两侧修改同一字段且值不同：冲突；
6. 一侧删除、另一侧修改：`delete_modify` 冲突；
7. 一侧新增且另一侧同身份新增不同内容：`add_add` 冲突；
8. 关系端点变化已经拆成删除和新增，按身份分别合并。

### 11.2 冲突解决

MVP 支持：

- `ours`：保留当前目标侧；
- `theirs`：采用来源侧；
- `manual`：提交完整顶层字段值，经规范化后生成新内容对象。

未解决冲突不能确认回写或升级。

### 11.3 合并结果验证

冲突全部解决后，必须对完整结果 Manifest 重新执行：

- 身份唯一性；
- 关系端点存在；
- 引用闭合；
- 业务结构验证；
- 模型健康；
- 求解准备。

## 12. 部分回写

### 12.1 三方输入

```text
Base   = 实例冻结基线
Ours   = 基线主线当前版本
Theirs = 实例当前版本中的选定变化
```

### 12.2 流程

1. 校验实例头和冻结基线；
2. 计算冻结基线到实例头的 Diff；
3. 接收用户选择的身份和顶层字段；
4. 计算最小依赖闭包；
5. 以基线主线为目标执行三方合并；
6. 保存变化项和冲突；
7. 解决冲突；
8. 验证完整合并结果；
9. 确认时再次检查基线主线未变化；
10. 创建新的基线 Revision；
11. 移动 `baseline_main`；
12. 保持实例头和冻结基线不变。

### 12.3 回写约束

- 回写不能直接改变实例；
- 回写不能绕过依赖闭包；
- 纯布局变化默认排除；
- 结构无效不能确认；
- 求解阻断允许明确确认后生成 `blocked` 基线；
- 基线主线变化后原请求标记 `stale`，必须重新预览。

## 13. 实例升级

### 13.1 三方输入

```text
Base   = 实例当前冻结基线
Ours   = 实例当前完整版本
Theirs = 目标基线版本
```

### 13.2 流程

1. 验证目标基线属于实例机台类型；
2. 验证目标基线不是当前冻结基线；
3. 加载三个完整 Manifest；
4. 自动合并基线变化和实例变化；
5. 解决冲突；
6. 验证完整实例结果；
7. 确认时再次检查实例头和目标基线有效；
8. 创建新的实例 Revision；
9. 新 Revision 的 `pinned_baseline_revision_id` 指向目标基线；
10. 移动 `instance_head`。

### 13.3 原子性

创建 Revision、移动实例头和更新实例兼容投影位于同一事务。失败时：

- 原实例头不变；
- 原冻结基线不变；
- 不产生可见半成品 Revision。

## 14. 有效模型解析

### 14.1 唯一路径

```text
machine
→ instance_head
→ RevisionStore.load_revision
→ KnowledgeModel
→ scope projection
→ effective-model/v2
→ precheck
→ Planner / Scheduler
```

预检查和正式求解必须调用同一个 resolver，不允许分别查询当前规范化表后自行拼装。

### 14.2 输入

- 正式实例 Revision；
- 明确的 canonical 原子活动范围；
- 目标状态范围；
- 当前状态、目标状态和临时条件等运行时输入。

活动包筛选必须在进入 resolver 前展开为 canonical 原子活动 ID 集合。

### 14.3 输出

```json
{
  "schema_version": "effective-model/v2",
  "knowledge_baseline_revision_id": "uuid",
  "knowledge_instance_revision_id": "uuid",
  "effective_model_hash": "sha256:...",
  "summary": {},
  "snapshot": {}
}
```

快照只保留重放所需的目标事实、候选原子活动、有效规则、关系、资源需求和必要日历解析结果，不保存数据库连接信息或密钥。

### 14.4 阻断

`blocked` 实例 Revision 不能求解，返回稳定错误码 `KNOWLEDGE_REVISION_SOLVER_BLOCKED`。

## 15. 求解记录与重放

### 15.1 保存内容

SolveRequest 或等价持久化结构新增：

- `knowledge_baseline_revision_id`；
- `knowledge_instance_revision_id`；
- `effective_model_schema_version`；
- `effective_model_hash`；
- `effective_model_summary`；
- `effective_model_snapshot`；
- 当前状态、目标状态和临时可用性等必要运行时快照。

### 15.2 重放条件

可重放必须满足：

- 知识 Revision 可读取并通过完整性校验；
- 有效模型 Schema 仍有兼容读取器；
- 必要运行时快照完整；
- 求解算法版本仍允许执行或已提供兼容适配。

条件不足时：

- 仍允许读取历史输入和结果；
- 返回具体缺失项；
- 不使用当前实例头版本代替历史版本。

### 15.3 旧求解记录

迁移前已保存 `effective-model/v1` 快照的求解记录继续按原快照读取。不得为旧记录伪造新的知识 Revision 引用。

## 17. 错误码

| HTTP | `error_code` | 含义 |
|---|---|---|
| 404 | `KNOWLEDGE_REVISION_NOT_FOUND` | Revision 不存在 |
| 404 | `KNOWLEDGE_SCOPE_NOT_FOUND` | 机台类型或实例不存在 |
| 409 | `KNOWLEDGE_MODE_DISABLED` | 当前部署模式未开放知识仓库业务 API |
| 409 | `KNOWLEDGE_WRITE_REQUIRES_VERSION_COMMIT` | enforced 模式禁止旧接口绕过版本提交 |
| 409 | `KNOWLEDGE_HEAD_CONFLICT` | 当前头版本与期望不一致 |
| 409 | `KNOWLEDGE_IDENTITY_CONFLICT` | 身份已存在或归属冲突 |
| 409 | `KNOWLEDGE_IDEMPOTENCY_KEY_REUSED` | 同幂等键对应不同请求 |
| 409 | `KNOWLEDGE_CHANGE_REQUEST_STALE` | 回写或升级目标头已变化 |
| 409 | `KNOWLEDGE_MERGE_CONFLICT_UNRESOLVED` | 仍有未解决冲突 |
| 409 | `KNOWLEDGE_REVISION_SOLVER_BLOCKED` | 版本不可用于求解 |
| 422 | `KNOWLEDGE_STRUCTURE_INVALID` | 草稿或合并结果结构错误 |
| 422 | `KNOWLEDGE_SOLVER_REVIEW_REQUIRED` | 有求解阻断，需要明确确认 |
| 422 | `KNOWLEDGE_DEPENDENCY_INCOMPLETE` | 选择项依赖不闭合 |
| 422 | `KNOWLEDGE_NO_CHANGES` | 提交没有有效变化 |
| 422 | `KNOWLEDGE_REPLAY_INPUT_INCOMPLETE` | 历史输入不足以重放 |
| 500 | `KNOWLEDGE_INTEGRITY_FAILURE` | 持久化内容完整性校验失败 |

错误响应必须包含：

```json
{
  "error_code": "KNOWLEDGE_HEAD_CONFLICT",
  "message": "当前版本已更新",
  "details": {},
  "current_head_revision_id": "uuid-or-null"
}
```

不得向前端暴露堆栈、SQL 或内部文件路径。

## 18. 幂等与并发

### 18.1 Commit

- 相同范围、相同 `idempotency_key`、相同规范请求返回原结果；
- 相同幂等键、不同规范请求返回 `KNOWLEDGE_IDEMPOTENCY_KEY_REUSED`；
- 版本号分配和 Ref 移动在同一行锁事务中完成。

### 18.2 回写和升级

- Preview 使用请求级幂等键；
- Confirm 对同一已确认请求重复调用返回原结果；
- Confirm 前重新检查目标头；
- 目标头变化时请求标记 `stale`，不能直接继续确认。

## 19. 初始化和迁移

### 19.1 迁移顺序

```text
013
→ 014 状态/活动本体引用统一
→ 015 知识版本仓库
```

015 为增量迁移，不物理删除旧表、旧字段或历史审计数据。

### 19.2 初始化工具

提供：

```text
dry-run
apply
verify
```

#### Dry-run

- 审计 014 已应用；
- 再次断言 Scope Guard 两表为零；
- 统计每个机台类型和实例将生成的对象、关系和内容对象；
- 检测跨机台引用、悬空关系和重复身份；
- 输出 Manifest Hash，不写库。

#### Apply

- 历史对象和关系生成确定性 UUIDv5；
- 每个机台类型生成首个 `B-000001`；
- 每个机台实例生成首个 `I-000001`；
- I1 复用继承基线的身份和内容哈希，并加入实例配置；
- I1 冻结到对应 B1；
- 创建 `baseline_main` 和 `instance_head`；
- 排除 Scope Guard、维护意图、虚拟活动和历史包级绑定。

#### Verify

- 重算全部内容哈希和 Manifest Hash；
- 验证 Ref 指向正确范围；
- 验证实例 Manifest 可独立恢复；
- 对比兼容投影；
- 使用固定实例执行预检和正式求解；
- 验证预检、求解和保存快照使用相同 `effective-model/v2`。

### 19.3 旧求解

不为迁移前求解记录自动填充知识 Revision。已有 `effective-model/v1` 快照继续保留。

## 20. 权威数据源切换

### 20.1 `off`

- 旧路径为权威；
- 知识仓库能力关闭；
- 仅允许迁移 dry-run。

### 20.2 `shadow`

- 旧路径继续服务；
- 同步构建 RevisionStore 模型；
- 比较对象数量、关系数量、模型哈希、预检和求解结果；
- 不让新仓库结果改变业务响应。

### 20.3 `enforced`

- RevisionStore 成为知识权威来源；
- 规范化表只作为当前头兼容投影；
- 所有编辑、导入、回写和升级必须经过 Commit；
- 禁止旧 API 绕过版本仓库直接修改求解知识。

切换必须由配置控制，默认值保持旧行为，符合 ANCHOR 的零侵入扩展原则。

### 21.5 业务验收

| Verify | 初始化工具、发布门禁和内部运维 |

没有前端入口的 `verify`、完整性重算和 shadow 对比属于内部能力。
