## 🧠 一、业务语义定义

### 1.1 阻塞的定义与范围

​**V0.2 仅处理"执行前阻塞"**​：步骤尚未开始，因准备度不足无法如期执行。

> ​**明确不在 V0.2 范围内**​：执行中阻塞（步骤进行中被中断）、外部系统推送阻塞信号、步骤执行状态实时追踪。

阻塞由​**计划师手动标记**​，系统不做自动检测。

---

### 1.2 两种阻塞处理策略

阻塞发生时，计划师在界面上选择策略，两种策略可单独使用或同时使用：

#### 策略 A — 活动提拉（离线修复）

```
业务语义：
  阻塞步骤 OPx 的修复在系统外部进行（离线）
  系统只需知道"OPx 在 T 之前不可执行"
  T 之后 OPx 视为自动可执行，重新进入排期
  修复过程不在系统内建模

系统行为：
  OPx 加入 not_before = T 约束（CP-SAT hard constraint）
  OPx 的资源在 T 之前释放给其他步骤
  RAG 中不依赖 OPx 的步骤被提拉，填满 [now, T] 窗口
  T 之后重新触发完整求解，OPx 自动进入排期

状态模型：
  不写入任何 blocked 特征
  OPx 的 precondition / effect 保持不变
  阻塞信息只存在于本次求解请求的参数中
​
```

#### 策略 B — 插入维修序列（攻关修复）

```
业务语义：
  阻塞需要专门的攻关维修工序介入
  维修序列预定义在规则库中
  维修序列执行完毕 = OPx 的 precondition 重新满足
  OPx 在维修序列完成后从头重新执行

系统行为：
  计划师标记阻塞原因（blockage_reason），写入当前机台状态特征
  重新触发完整求解，求解器自动匹配维修序列（precond 匹配 blockage_reason）
  维修序列插入 OPx 之前，其 effect 恢复 OPx 所需 precondition
  生成新版本计划

状态模型：
  阻塞原因作为机台状态特征参与 precond/effect 推导
  feature_key:   "blockage_reason"
  feature_value: "hardware_fault" / "pending_approval" 等
  维修序列的 precondition 匹配对应 blockage_reason
  维修序列的 effect 清除 blockage_reason 特征，恢复 OPx precondition
​
```

#### 策略 A + B 同时使用

```
场景：较大阻塞，攻关（策略B）同时并行推进其他可执行步骤（策略A）

系统行为：
  同时应用两套约束：
    → 写入 blockage_reason 特征（触发维修序列自动插入）
    → OPx 加入 not_before = T 约束
  CP-SAT 在同一资源池内同时排期：
    → 维修序列（OP_REPAIR）
    → 被提拉的其他 RAG 步骤
  两者共享资源池，CP-SAT 负责仲裁资源冲突

注意：
  OP_REPAIR 的 duration 是规则库中预定义的固定值
  not_before T 由计划师根据预估攻关时长手动指定
  两者不必相等，CP-SAT 取两个约束的最晚结束时间
​
```

---

### 1.3 求解模式

​**V0.2 采用一次性完整重新求解**​，不做增量重排：

```
触发时机：计划师标记阻塞并配置策略后，手动点击"重新求解"
求解起点：计划师人工告知"当前状态"（人工感知已完成步骤）
求解过程：复用 V0.1 完整求解链路（状态推导 RAG + CP-SAT）
          在 CP-SAT 建模阶段叠加阻塞约束
输出结果：生成新版本计划（版本号递增）
​
```

## 🗄️ 二、数据模型扩展

V0.2 在 V0.1 数据模型基础上扩展，不修改已有表结构，只新增字段和表。

### 2.1 solve\_request 表扩展

在已有 `solve_request` 表新增字段：

```sql
ALTER TABLE solve_request ADD COLUMN parent_plan_id INTEGER REFERENCES candidate_plan(id);
-- 记录本次求解是基于哪个版本重排的，用于版本链追溯
-- 初次求解时为 NULL，重排时指向被重排的计划版本
​
```

### 2.2 candidate\_plan 表扩展

```sql
ALTER TABLE candidate_plan ADD COLUMN version      INTEGER NOT NULL DEFAULT 1;
ALTER TABLE candidate_plan ADD COLUMN parent_plan_id INTEGER REFERENCES candidate_plan(id);
ALTER TABLE candidate_plan ADD COLUMN replan_reason VARCHAR(64);
-- replan_reason 枚举值：'initial' / 'blockage_strategy_a' / 'blockage_strategy_b' / 'blockage_strategy_ab'
​
```

### 2.3 candidate\_plan\_step 表扩展

```sql
ALTER TABLE candidate_plan_step ADD COLUMN not_before       INTEGER;
-- 单位：分钟，相对于计划起点的偏移量
-- 策略 A 时由计划师指定，NULL 表示无约束

ALTER TABLE candidate_plan_step ADD COLUMN step_role        VARCHAR(32);
-- 枚举值：'normal'（正常步骤）/ 'repair'（维修序列）/ 'pulled_forward'（被提拉步骤）
-- 用于前端版本对比时的差异标注
​
```

### 2.4 新增 blockage\_event 表

```sql
CREATE TABLE blockage_event (
    id                SERIAL PRIMARY KEY,
    plan_id           INTEGER NOT NULL REFERENCES candidate_plan(id),
    blocked_step_id   INTEGER NOT NULL REFERENCES candidate_plan_step(id),
    strategy          VARCHAR(8) NOT NULL,
    -- 枚举值：'A' / 'B' / 'AB'

    -- 策略 A 字段
    not_before_offset INTEGER,
    -- 单位：分钟，相对于计划起点，计划师手动指定

    -- 策略 B 字段
    blockage_reason   VARCHAR(64),
    -- 写入机台状态特征的值，同时作为维修序列 precondition 的匹配键

    created_at        TIMESTAMP NOT NULL DEFAULT NOW(),
    created_by        VARCHAR(64),
    note              TEXT
);
​
```

## ⚙️ 三、求解链路扩展

### 3.1 扩展点总览

V0.2 在 V0.1 两层架构基础上，在**第二层（CP-SAT 建模）** 叠加阻塞约束，第一层（状态推导 RAG）的扩展只针对策略 B（需要自动插入维修序列）：

```
┌─────────────────────────────────────────────────────┐
│  第一层：状态推导 RAG（扩展点）                       │
│                                                     │
│  策略 A：无变化，RAG 照常生成                         │
│  策略 B：当前状态含 blockage_reason 特征              │
│          → precond/effect 推导自动匹配维修序列        │
│          → 维修序列节点插入 RAG，连接到阻塞步骤之前   │
└──────────────────────────┬──────────────────────────┘
                            │ RAG（含维修序列节点）
┌──────────────────────────▼──────────────────────────┐
│  第二层：CP-SAT 建模（扩展点）                        │
│                                                     │
│  新增约束 1（策略 A）：                               │
│    model.Add(start[OPx] >= not_before_offset)        │
│                                                     │
│  新增约束 2（策略 A + B 共用）：                      │
│    资源池约束不变，CP-SAT 自动仲裁                    │
│    被提拉步骤的排期自然填入 not_before 窗口           │
│                                                     │
│  step_role 标注（求解后写入）：                       │
│    对比父计划，新增步骤标注 'repair' / 'pulled_forward'│
└─────────────────────────────────────────────────────┘
​
```

### 3.2 策略 B 的维修序列规则库约定

维修序列必须在 `op_rule` 表中满足以下约定：

```
op_rule:
  code:       'OP_REPAIR_*'（命名约定，便于查询和管理）
  is_repair:  TRUE（新增布尔字段，标识为维修类型工序）

op_rule_precond（维修序列的前置条件）：
  feature_key:   'blockage_reason'
  feature_value: '<对应阻塞原因>'   ← 与 blockage_event.blockage_reason 匹配

op_rule_effect（维修序列的执行效果）：
  效果1：清除 blockage_reason
    feature_key:   'blockage_reason'
    new_value:     'none'
  效果2：恢复阻塞步骤所需的 precondition
    feature_key:   '<阻塞步骤需要的特征>'
    new_value:     '<恢复值>'
​
```

```sql
-- op_rule 表新增字段
ALTER TABLE op_rule ADD COLUMN is_repair BOOLEAN NOT NULL DEFAULT FALSE;
​
```

## 📦 五、V0.2 方向二开发顺序

```
Step 1 — 数据模型扩展
  执行 ALTER TABLE / CREATE TABLE
  op_rule 新增 is_repair 字段
  新增维修序列种子数据（至少 2 条，对应 2 种 blockage_reason）

Step 2 — 策略 A 实现（纯 CP-SAT 约束扩展）
  solve_request 接受 blockage_constraints 参数
  scheduler/model.py 新增 not_before 约束注入
  验收：OPx 的排期不早于指定时间，其他步骤自动填入窗口

Step 3 — 策略 B 实现（状态特征 + RAG 扩展）
  solve 接口接受 blockage_reason 参数，写入当前状态特征
  planner/matcher.py 自动匹配 is_repair=TRUE 的维修序列
  验收：求解结果中出现 OP_REPAIR 节点，位于 OPx 之前

Step 4 — 版本管理
  candidate_plan 版本链写入
  blockage_event 记录
  GET /api/v1/plans/{id}/versions 接口

Step 5 — 前端 BlockageDialog 组件
  策略选择 + 参数填写 + 触发重新求解

Step 6 — 前端版本对比甘特图
  并排展示 + step_role 颜色标注
​
```

## ⚠️ AI 编程助手注意事项

1. ​**不破坏 V0.1 链路**​：所有扩展通过新增字段/表和参数注入实现，不修改已有求解逻辑的默认行为。阻塞约束参数为空时，行为与 V0.1 完全一致
2. ​**策略 B 的维修序列匹配走已有 precond/effect 推导链路**​，不为阻塞单独开发匹配逻辑
3. ​**step\_role 标注在 CP-SAT 求解完成后通过与父计划 diff 计算**​，不在求解过程中实时标注
4. ​**not\_before 约束单位统一为分钟**​，与 `duration_min` 保持一致
5. ​**blockage\_reason 的合法值由 op\_rule\_precond 表中已有的 feature\_value 决定**​，前端下拉列表动态从数据库读取，不硬编码枚举值
