# 目标业务系统差距评估

> 日期：2026-06-05
> 状态：评估稿 v1
> 目的：基于真实业务系统和已有活动资料库，评估建设数据管理能力与
> 求解 / 排程引擎所需的工作内容、阶段路线和工作量。

## 1. 评估前提

当前 demo 工程只作为技术验证参考，不作为真实业务系统的直接改造基线。
真实评估基线来自现有业务系统：

- 已有独立开发的活动资料库系统；
- 已有活动序列管理和活动 SOP 归档能力；
- 暂无正式求解引擎；
- 需要在既有业务系统和活动资料库基础上建设数据管理、规则治理、
  求解和完整排程能力。

目标不是简单把 demo 求解器接入现有数据库，而是建设一个能逐步承接真实
多子系统协作、活动变更、维修维护插入和小时级完整排程的业务系统。

## 2. 已确认现状

### 2.1 活动资料库

现有活动资料库是一个独立开发系统，具备活动序列管理和活动 SOP 归档。
活动资料规模约 3000+ 条，可导出 Excel。

当前活动字段包括：

- 活动名称；
- 活动编号；
- 所属系统；
- 人工编写的前置条件文字；
- 工时；
- 作业人数；
- 所需 BOM；
- 工装 BOM 编号和数量。

活动层级为：

```text
集成项目 -> 里程碑 -> 活动块 -> 活动项
```

维修维护活动也在同一个活动资料库中。

### 2.2 规则和依赖

当前活动资料只有前置条件文字字段，没有结构化输出结果字段。前置条件写法
相对自由，不是固定模板。

这意味着当前资料库尚不能直接自动生成求解需要的 provider/consumer 关系：

```text
某活动需要什么事实
某活动提供什么事实
```

现有前置条件文字可以作为 consumer fact 的来源，但还需要补建活动输出结果，
才能知道哪些活动能提供这些事实。

### 2.3 顺序数据

现有业务中有两套与活动顺序相关的数据：

- 序列设计系统：主要表达推荐顺序；
- 历史人工计划顺序：记录人工实际编排经验。

这两类顺序不宜直接固化为硬 DAG。更合理的使用方式是：

- 推荐顺序作为软约束；
- 历史人工顺序作为经验样本；
- 用于默认排序、活动组连续性、计划规律性和偏离说明。

### 2.4 状态来源

当前状态来自集成计划管理系统，来源包括人工维护和 logbook 同步。活动完成
状态可以关联到活动编号。

这为后续从执行记录反推当前状态提供了基础，但由于活动缺少输出结果字段，
仍需要补齐“完成某活动后改变哪些状态 / 产生哪些交付事实”的语义。

### 2.5 资源和排程边界

目标是完整排程，不只是输出逻辑活动顺序。排程精度要求为小时级。

首要资源维度为：

- 场地；
- 吊装；
- 工装。

人员暂不作为第一阶段核心排程资源。当前没有人员专业、班组、班次等信息，
用户判断人员问题短期不显著。

现有资源数据成熟度如下：

| 资源 | 当前状态 | 判断 |
| --- | --- | --- |
| 工装 | 有工装 BOM 编号和数量 | 可作为首期资源需求入口 |
| 吊装 | 只有“需要吊装”字段 | 只能先做简化约束 |
| 场地 | 暂无结构化数据 | 需要补建资源模型 |
| 人员 | 有作业人数，无班组班次 | 首期暂不排 |
| BOM | 有所需 BOM，未来系统会有齐套 / 库存 / 到货能力 | 首期可预留，不作为核心复杂点 |

### 2.6 目标业务场景

目标业务系统至少要覆盖三类场景：

1. 从 0 生成完整活动计划初稿；
2. 活动变更后快速生成调整部分计划；
3. 维修维护计划的插入和制定。

目标计划定义方式可能不止一种：

- 按集成项目 / 里程碑 / 阶段选择；
- 人工指定一组活动范围；
- 将维修维护活动插入已有计划。

用户希望 2026 年内先上线一版可用系统。

## 3. 目标业务系统

目标系统应定义为：

> 在既有活动资料库和集成计划管理系统基础上，建设一个可治理、可解释、
> 可渐进落地的多子系统计划生成与排程系统。系统能够把活动资料库中的
> 文字 / 半结构化资料逐步转化为标准事实和活动规则，基于当前状态、
> 目标范围和资源约束自动生成小时级活动排程，并在活动变更、维修维护
> 插入和状态变化下支持重排、解释和差距诊断。

### 3.1 数据管理目标

数据管理侧要从“活动资料管理”升级为“规则知识库治理”：

- 活动资料统一接入；
- 前置条件文字可映射为标准事实；
- 补建活动输出结果字段；
- 建立标准事实词典，包括定义、归属、值域、单位和生命周期；
- 活动通过事实表达依赖，而不是直接维护全局活动依赖；
- 保留集成项目、里程碑、活动块、活动项的管理视图；
- 建立规则健康检查能力，包括孤儿事实、无 provider 条件、循环风险、
  写冲突、资源缺口、歧义映射；
- 支持规则映射、目标模板、计划结果和版本变更追踪。

### 3.2 求解引擎目标

求解引擎至少需要两层：

```text
Planner
  从目标、状态、前置条件、输出事实和推荐顺序生成活动偏序。

Scheduler
  在场地、吊装、工装等资源约束下生成小时级时间排程。
```

引擎需要支持：

- 从 3000+ 活动资料中召回目标相关活动；
- 基于 provider/consumer fact 自动建图；
- 推荐顺序和历史人工计划顺序作为软约束；
- 硬约束保证物理、工艺、安全和接口可执行；
- 软约束保证计划规律性，例如同组连续、少切换、主线优先；
- 活动变更后的影响范围分析和局部调整；
- 维修维护活动插入已有计划；
- 无解、缺数据、资源冲突时给出诊断。

### 3.3 用户操作目标

用户不应逐项维护大量状态。目标操作方式应是：

- 计划员选择集成项目、里程碑、活动块或活动范围；
- 系统读取当前活动完成状态和已同步状态；
- 系统提示缺失或未结构化的前置 / 输出事实；
- 业务人员或规则管理员确认事实映射；
- 系统生成小时级排程和冲突诊断；
- 计划员查看推荐顺序偏离、资源冲突和不可排原因。

## 4. 核心差距

### 4.1 数据语义差距

最大差距是规则语义尚未结构化。

当前只有自由文本前置条件，没有结构化输出结果。求解引擎无法仅凭这些字段
可靠判断：

```text
活动 A 为什么要在活动 B 后面？
活动 C 完成后满足了哪些后续活动条件？
某个前置条件没有 provider，是数据缺失还是业务确实不可达？
```

因此，首要工作不是直接开发排程算法，而是建立：

- 标准事实词典；
- 前置条件文字到事实的映射流程；
- 活动输出结果补录机制；
- provider/consumer 自动建图；
- 缺失关系诊断。

### 4.2 资源模型差距

完整排程要求考虑场地、吊装、工装，但三类资源当前成熟度不同。

工装已有 BOM 编号和数量，可以优先建最小资源需求模型。吊装只有“需要吊装”
字段，只能先做布尔或容量类简化约束。场地没有结构化数据，首版如果要纳入
场地，就必须补建场地编号、可用性、活动适用范围、容量或互斥规则。

### 4.3 状态和目标差距

活动完成状态能关联活动编号，这是优势。但缺少输出结果字段，使得“活动完成”
无法自动转化为标准状态变化。

目标定义也存在多入口：里程碑、阶段、人工活动范围、维修维护插入。后续需要
统一抽象为：

```text
目标范围 + 目标事实 + 候选活动集合
```

### 4.4 计划规律性差距

现有推荐序列和历史人工计划顺序是宝贵经验，但不能直接作为硬依赖。否则 DAG
会过度线性，活动变更或维修维护插入后几乎没有调整空间。

需要将这些顺序转为软约束和代价函数：

- 尽量遵守推荐顺序；
- 尽量保持活动块连续；
- 尽量减少跨系统切换；
- 允许在阻塞、资源冲突或维护插入时打破推荐顺序；
- 输出偏离原因。

## 5. 推荐首版范围

考虑 2026 年内上线一版，首版应控制为“可导入、可结构化、可排一版、
可解释差距”，不建议直接承诺全量自动化。

### 5.1 首版建议输入

```text
Excel 导出的活动资料库
选定集成项目 / 里程碑 / 活动块范围
人工确认后的标准事实映射
补录后的活动输出结果
工装 BOM 编号和数量
简化吊装字段
集成计划管理系统中的活动完成状态
推荐顺序和历史人工计划顺序
```

### 5.2 首版建议输出

```text
小时级活动排程
活动依赖关系
工装占用冲突提示
简化吊装需求冲突提示
推荐顺序偏离说明
缺失前置 / 缺失输出 / 无 provider 诊断
无解 / 缺数据诊断
排程结果导出或回写
```

### 5.3 首版不建议承诺

- 全 3000+ 活动一次性全部自动结构化；
- 完整场地资源调度；
- 完整吊装设备能力建模；
- BOM 到货 / 库存联动；
- 完全自动从自由文本理解所有前置条件；
- 成熟高级增量重规划；
- 多项目横向资源协调；
- 人员班组和班次排程。

## 6. 分期路线

### Phase 0：资料盘点和试点选择

目标是选择一个可控范围，明确 Excel 字段结构、数据质量和试点边界。

建议试点范围：

```text
1 个集成项目
2-3 个里程碑
100-300 条活动
```

交付物：

- Excel 字段解析报告；
- 活动层级和编码校验；
- 前置条件文本样本分类；
- 推荐序列和历史计划序列样本分析；
- 试点范围确认。

### Phase 1：规则库治理底座

目标是让试点范围内的活动具备可建图语义。

交付物：

- 标准事实词典；
- 前置条件文字映射流程；
- 活动输出结果补录流程；
- provider/consumer 关系生成；
- 规则健康检查雏形；
- 缺失事实、无 provider、歧义映射诊断。

### Phase 2：最小 Planner

目标是从目标范围和当前状态生成活动偏序。

交付物：

- 目标相关活动召回；
- 硬约束依赖建图；
- 推荐顺序软约束；
- 历史人工计划顺序参考；
- 活动变更影响范围初步分析；
- 无解 / 缺数据诊断。

### Phase 3：最小 Scheduler

目标是生成小时级排程。

交付物：

- 小时级时间排程；
- 工装资源约束；
- 简化吊装约束；
- 推荐顺序偏离说明；
- 排程结果展示和导出；
- 冲突诊断。

### Phase 4：集成和试点上线

目标是接入真实业务流程，完成首版试用。

交付物：

- 活动资料 Excel 接入；
- 集成计划管理系统状态接入；
- 试点排程联调；
- 计划结果导出 / 回写；
- 用户验收；
- 数据修正闭环。

## 7. 工作量估算

以下估算以“2026 年内上线首版”为目标，假设先做试点范围，而不是一次性覆盖
全 3000+ 活动。

| 阶段 | 内容 | 粗略周期 | 粗略人力 |
| --- | --- | --- | --- |
| Phase 0 | 现状盘点、样本抽取、Excel 字段剖析、试点范围确定 | 2-4 周 | 1 产品/业务分析 + 1 后端/数据 |
| Phase 1 | 标准事实词典、文本映射流程、输出结果补录、规则健康检查雏形 | 6-10 周 | 1 产品/业务分析 + 2 后端/数据 + 1 前端 |
| Phase 2 | 最小 Planner：provider/consumer 建图、硬约束、推荐顺序软约束、诊断 | 8-12 周 | 2 算法/后端 + 1 后端 |
| Phase 3 | 最小 Scheduler：小时级排程、工装约束、简化吊装约束、结果展示/导出 | 6-10 周 | 1 算法/后端 + 1 后端 + 1 前端 |
| Phase 4 | 状态接入、试点联调、验收、数据修正闭环 | 4-8 周 | 1 后端 + 1 前端 + 业务专家持续参与 |

首版总量级：

```text
周期：约 4-7 个月
人力：约 18-30 人月
```

如果首版要求覆盖全 3000+ 活动，并完整支持场地、吊装、BOM 和成熟局部
重规划，工作量会明显上升：

```text
周期：约 9-15 个月
人力：约 45-80 人月
```

## 8. 关键风险

1. 前置条件自由文本比例高，结构化转换工作量可能被低估。
2. 没有活动输出结果字段，是自动建图的最大数据缺口。
3. 场地和吊装资源数据不足，会限制完整排程可信度。
4. 推荐序列 / 历史顺序如果被误当成硬约束，会导致计划过度线性。
5. 如果首版直接追求全库覆盖，2026 年内上线风险较高。
6. 业务专家参与不足，会导致事实词典和输出结果映射质量不稳定。
7. 如果资源模型补建和求解引擎开发并行失控，容易出现“算法能跑，
   但数据不可用”的情况。

## 9. 建议立即启动的 PoC

选择一个可控试点，先验证“数据能否被结构化到可求解程度”。

```text
范围：
  1 个集成项目
  2-3 个里程碑
  100-300 条活动

验证：
  前置条件文字映射成功率
  输出结果补录工作量
  provider/consumer 自动建图质量
  推荐序列作为软约束后的排程规律性
  工装约束和简化吊装约束的排程效果
  小时级排程结果是否被业务接受
```

PoC 通过后，再决定扩展到 1000+ / 3000+ 活动范围。

## 10. 待确认事项

后续进入实施前，还需要确认：

- 现有活动资料库 Excel 的实际字段样例；
- 前置条件文字的典型写法和高频模式；
- 输出结果是否能由业务专家按活动块批量补录；
- 场地资源是否必须进入首版，还是可先作为诊断项；
- 吊装是否能补充设备 / 吊点 / 窗口 / 能力信息；
- 工装 BOM 编号是否能映射到可占用资源实例；
- 集成计划管理系统是否支持状态数据导出或接口读取；
- 首版试点项目和里程碑范围；
- 结果回写方式：Excel、接口、还是人工导入。
