> **生成时间：** 2026-04-25
> **项目版本：** V0.3（数值型状态规划 Phase 1 已完成）
> **报告目的：** 串联需求→实现→差距→方向，明确项目愿景与重点开发方向

## 一、执行摘要（一页纸）

### 项目定位
**泵体机械集成场景的自动化计划求解系统**。给定机台的起点状态、目标状态、工序规则库和资源约束，自动推导合法工序路径（RAG）并生成最优排程（CP-SAT），支持计划师对阻塞情况进行动态重排。

### 当前状态（V0.3）
- ✅ **工程闭环成熟**：Planner → Scheduler → API → UI 全链路跑通
- ✅ **阻塞处理闭环**：策略 A/B/AB 已实现，支持版本链追踪
- ✅ **数值型规划落地**：Phase 1 完成，支持重复步骤实例化
- ⚠️ **核心语义层有差距**：Planner 仍是启发式拼装器，非需求定义的最小代价搜索器
- ⚠️ **人工替代率约 35%-45%**：常规排程可达 60%，但 What-if/规则校验/异常恢复几乎空白

### 核心差距（Top 5）
| # | 差距 | 影响 | 优先级 |
|---|------|------|--------|
| 1 | Planner 求解范式差距（启发式拼装 vs 最小代价搜索） | 无法保证全局最优，不可达判定不严谨 | 🔴 P0 |
| 2 | 目标模型语义未对齐（state_id vs 条件表达式 G） | 无法表达复杂目标条件 | 🔴 P0 |
| 3 | 效果可交换性并行过滤层缺失 | 可能误判并行（如上电+下电） | 🔴 P0 |
| 4 | 数值触发是"步进规划"而非"事件驱动循环" | 未建模维护闭环 | 🔴 P0 |
| 5 | 多目标优化 weight 字段被忽略 | 架构性缺口，V0.3 STEP 2 被阻塞 | 🟡 P1 |

### 路线图速览
- **短期（V0.4，2-3月）**：冻结四层语义 + 求解可解释性 + Excel 导入
- **中期（V0.5-V0.8，6-9月）**：A*搜索 + 工序组 + What-if + 规则校验
- **长期（V1.0，12月+）**：多项目隔离 + MES 集成 + 实时追踪 + 鲁棒排程

## 二、项目愿景与定位

### 2.1 一句话定义
> **规则驱动的状态空间求解引擎 + 计划师操作界面。**

本质：可配置求解平台（单项目、单起终点）。规则库通过界面维护，新规则加入无需改代码。

### 2.2 核心价值主张
> **利用工具及时、准确地生成序列和计划，最大程度减少对人的依赖。**

当前人工依赖集中在：
1. **规则库维护**（定义 op_rule / precond / effect）
2. **阻塞策略选择**（A/B/AB 需计划师手动决策）
3. **异常恢复处理**（状态回退后人工重规划）
4. **工艺规则校验**（人工检查模板库健康度）

### 2.3 设计原则（支撑"减少人工依赖"）

| 原则 | 如何减少人工依赖 |
|------|-----------------|
| **规则内置，数据驱动** | 新增工序 = 数据库 INSERT，不改代码 |
| **模块解耦，接口稳定** | 任一模块可替换，不影响整体 |
| **策略模式，注册优于修改** | 新增 Operator/Effect/Objective = 注册新类 |
| **零侵入扩展** | 新参数有默认值，不传时行为一致 |
| **可解释性优先于精度** | 结果必须能说明"为什么是这个顺序" |

### 2.4 明确不在范围内（V1.0 前不碰）
- ❌ 多项目隔离
- ❌ 角色权限管理
- ❌ 跨机台资源调配
- ❌ 实时执行状态追踪（步骤级别）
- ❌ 外部系统推送阻塞信号
- ❌ 执行中阻塞（进行中被中断）
- ❌ 工序时长不确定性建模（鲁棒排程）
- ❌ 技能匹配约束

### 3.1 四大业务场景

| 场景 | 触发时机 | 当前支持 | 人工替代率 | 目标 |
|------|---------|---------|-----------|------|
| **场景1: 常规排程** | 每日/每班次排程前 | ✅ 基本支持 | ~60% | 90% |
| **场景2: What-if 预演** | 工艺优化讨论 | 🚧 部分支持 | ~20% | 80% |

| **场景4: 异常恢复** | 模块返工/替换 | ❌ 未开始 | 0% | 60% |

### 3.2 P0/P1/P2/P3 需求优先级

**P0（必须实现）：**
- 最小代价路径求解 + 条件满足型目标
- 不可达判定 + 路径可解释输出
- 效果可交换性并行验证
- 秒级响应 + ≤70 步 + 500+ 模板

**P1（重要）：**
- 并行关系自涌现 + 偏序图输出
- What-if 参数对比

**P2（有用）：**
- 工艺规则离线校验（死锁/冗余/循环）

**P3（未来）：**
- 异常恢复重规划

### 3.3 核心 KPI
- **秒级响应**：单次求解 < 5 秒
- **路径长度**：≤70 步（典型 ~50 步）
- **模板库规模**：500+ 规则
- **主线占比**：≥70%
- **结果可解释**：每步状态变化、效果执行、前置判定可追溯
- **自动触发**：sub 归零 → 自动触发 → reset 恢复阈值

## 四、系统架构与模块交互

### 4.1 分层架构（锁定）

```
┌─────────────────────────────────────────┐
│  表示层 — Vue 3 + Element Plus          │
├─────────────────────────────────────────┤
│  应用层 — FastAPI 路由                   │
├─────────────────────────────────────────┤
│  服务层 — 业务编排（当前缺失）            │
├─────────────────────────────────────────┤
│  领域层 — 求解核心 (solver/)             │
│  RuleEvaluator / StateDelta /           │
│  RAGBuilder / Scheduler                 │
├─────────────────────────────────────────┤
│  持久层 — PostgreSQL / SQLAlchemy ORM    │
└─────────────────────────────────────────┘
```

**跨层调用规则：** 只能调用相邻下层，不可跨层。

### 4.2 端到端求解链路

```
POST /api/v1/solve
  │
  ├─→ [阶段1] 输入校验（machine/state/objective）
  ├─→ [阶段2] Planner.build_rag() → RAG (nodes + edges)
  ├─→ [阶段3] 持久化 candidate_plan + candidate_plan_step
  ├─→ [阶段4] 应用策略A约束（not_before）
  ├─→ [阶段5] Scheduler.solve_schedule() → CP-SAT 最优排程
  ├─→ [阶段6] 持久化 schedule_result + step_role diff
  └─→ [阶段7] 响应组装（makespan + tasks + parallel_groups）
```

### 4.3 核心领域模块

| 模块 | 职责 | 当前实现状态 |
|------|------|-------------|
| **RuleEvaluator** | precond 匹配和 effect 应用的唯一入口 | ✅ 注册表化 |
| **StateDelta** | 计算起点与目标的状态差 | ✅ 已实现 |
| **RAGBuilder** | 状态差 → 工序 DAG | 🚧 启发式拼装，非最小代价搜索 |
| **Scheduler** | 工序 DAG → CP-SAT 排程 | ✅ 基本功能完整 |

### 4.4 人工介入点分析

| 位置 | 介入内容 | 自动化潜力 |
|------|---------|-----------|
| 规则库维护 | 定义 op_rule / precond / effect | 中（Excel 导入） |
| 策略A: not_before 时间 | 手动输入离线修复时长 | 高（历史数据推荐） |
| 策略B: blockage_reason | 选择阻塞原因 | 中（故障模式库） |

## 八、技术债务与风险（详细）

### 8.1 求解范式差距（最高风险）

**现状：** Planner 是 "delta 匹配 + precondition/provider 递归补齐" 的启发式拼装器。

**需求：** 从 s₀ 到目标条件集合 G 的最小代价可达路径搜索。

**差距影响：**
- ❌ 不能严格保证全局最小代价
- ❌ 不可达判定基于递归失败而非状态空间穷尽
- ❌ 无法支持 What-if 分析（需要搜索空间探索）
- ❌ 无法支持规则校验（需要死锁/循环检测）

**建议：** 冻结 Planner 搜索语义，明确是继续优化启发式还是迁移到 A*/Dijkstra。

### 8.2 目标模型语义差距

**现状：** API 要求 `current_state_id` + `target_state_id`（数据库预定义状态快照）。

**需求：** 目标 G 应为条件表达式（如 `洁净状态 > 100`），纯 AND 逻辑。

**差距影响：**
- ❌ 无法直接表达条件型目标
- ❌ 目标输入被绑定到预定义状态对象
- ❌ 无法支持部分目标达成（如只关心某几个特征）

### 8.3 数值触发语义差距

**现状：** numeric 实现是 `increment/decrement` 风格的 exact target 多步推进。

**需求：** `sub` 逐步下降 → 归零事件 → 自动触发关联活动 → `reset` 恢复阈值。

**差距影响：**
- 🚧 当前 numeric 更像"数值步进规划"
- ❌ 不是需求中的"触发式维护循环"
- ❌ 未建模事件驱动的维护闭环

### 8.4 效果可交换性缺失

**现状：** `find_parallel_groups()` 仅按"相同 predecessor 集合"分组。

**需求：** 双层过滤：① 偏序图无路径 ② 共享 key 操作可交换。

**差距影响：**
- ❌ 两个无前驱步骤若修改同一 feature 会被误判为可并行
- ❌ 典型冲突：上电 + 下电共享 `电源状态` 且都是 `set`
- ✅ Scheduler 最终兜底正确（时间重叠检测），但 Planner 阶段不严谨
