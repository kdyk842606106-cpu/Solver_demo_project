# Solver Demo Project 全景梳理与差距分析报告（修订版）

> **生成时间：** 2026-04-25
> **项目版本：** V0.3
> **核心价值主张：** 利用工具及时、准确地生成序列和计划，最大程度减少对人的依赖

---

## 一、项目愿景：我们需要什么

### 1.1 一句话定义
> **面向复杂装备集成的自动化计划求解引擎**

给定机台的**当前状态**和**目标条件**，基于预定义的工序规则库和资源约束，自动生成：
- ✅ 合法工序序列（做什么）
- ✅ 最优执行顺序（按什么顺序做）
- ✅ 精确时间安排（何时做、用何资源）
- ✅ 阻塞动态重排（遇到异常怎么办）

**核心目标：让系统替代计划师完成"从状态到计划"的全链路推导。**

### 1.2 为什么需要这个系统（业务痛点）

以**泵体机械集成**为例：
- 单个泵体由多个功能模块组成（A模块、B模块、C模块...）
- 每个模块涉及安装、调测、测试、清洁、拆卸、维护等操作
- 工序之间存在复杂前置依赖（如上电后才能调测，建真空前必须下电）
- 状态可回退（模块可拆卸返工，非单向累积）
- 数值触发维护（每安装N次必须清洁）
- **手工编排**：500+活动模板、几十个模块、复杂依赖，人工编排耗时长且容易遗漏

### 1.3 期望的人工替代率

| 能力维度 | 当前人工依赖 | 目标 | 替代空间 |
|---------|-------------|------|---------|
| 常规排程 | 计划师手工编排 | 系统一键生成 | 90% |
| What-if 预演 | 专家经验判断 | 秒级参数对比 | 80% |
| 规则库校验 | 人工逐项检查 | 离线自动诊断 | 70% |
| 异常恢复 | 人工重规划 | 自动状态回退重算 | 60% |

## 二、实际业务场景：怎么用

### 场景1：常规排程（每天/每班次使用）

**使用流程：**
```
工程师选择机台 → 录入当前现场进度（起点状态）→ 选择目标状态
  → 系统自动求解
  → 输出：甘特图 + 工序列表 + 并行组 + 关键路径
  → 工程师审查确认 → 下发执行
```

**典型业务细节：**
- 起点：`模块A已安装、模块B待调测、电源下电、安装缺口=2`
- 目标：`所有模块已调测、电源上电、真空建立`
- 系统自动推导出的序列可能包含：
  - 上电 → A调测 → 下电 → 建真空 → B调测 → 再上电 → ...
  - **关键特征**：上电/下电可能反复出现，由前置约束网络自然决定，非人工预设
  - 安装缺口归零 → 自动触发清洁 → 重置回阈值（数值触发自涌现）

**对系统的核心要求：**
- 秒级响应
- 结果可解释（能说明"为什么先做这个"）
- 自动处理数值触发规则
- 主线活动自然涌现（不由人工预定义骨架）

### 场景2：What-if 预演（工艺优化讨论）

**使用场景：**
- "如果把清洁阈值从10改为8，总活动数会增加多少？"
- "新增D模块调测后，整体路径如何变化？"
- "提高调测活动权重，路径会不会避开高成本方案？"

**系统应输出：**
- 新旧方案对比表
- 参数敏感性结论（如"sub幅度从1→2，清洁次数-1，总步数-1"）

### 场景3：规则库校验（定期维护）

**使用场景：**
- 新增活动模板后，验证是否与现有规则冲突
- 检查是否存在死锁、冗余、循环风险

**系统应输出：**
- 死锁检测报告
- 冗余活动报告
- 循环风险报告

### 场景4：异常恢复（未来扩展）

**使用场景：**
- 某模块返工，外部系统更新状态为"待调测"
- 系统从新的起点状态自动重规划
- 对比新旧路径，标记需要返工的部分

## 四、现有 Demo 与愿景的核心差距

### 4.1 差距总览

当前系统已具备**工程闭环**（Planner→Scheduler→API→UI 全链路跑通），但在**核心求解能力**上与愿景存在根本性差距。

**一句话总结：**
> 当前是"基于状态差分的逆向工序拼装器"，愿景是"基于状态空间正向搜索的路径规划器"。
> 这决定了系统能否处理复杂长链路场景（如反复上下电、状态回退、动态数值触发）。

### 4.2 核心差距1：求解范式 — 逆向拼装 vs 正向搜索（🔴 最高优先级）

**当前实现（逆向拼装）：**
```
目标状态 G ──→ 计算差分 Δ ──→ 逆向找能产生 Δ 的工序
  └──→ 检查工序的前置条件 ──→ 递归找前置工序 ──→ ...
```

**问题本质：**
- 系统是**从目标倒推**需要哪些工序
- 适合简单场景（状态单向变化、工序一次性执行）
- 但对于**长链路场景**（如反复上下电）会出现问题：
  - 例：起点（下电）→ 目标（上电+调测完成）
  - 实际需要：上电 → 调测 → 下电 → 建真空 → 再上电 → ...
  - 逆向拼装可能无法正确推导"下电后再上电"这种**状态回退后重新推进**的序列

**愿景要求（正向搜索）：**
```
起点状态 s₀ ──→ 搜索所有可达状态 ──→ 找到到达 G 的最小代价路径
  └──→ 维护已访问状态集合（避免循环）
  └──→ 逐步应用 effect 推进状态
  └──→ 支持状态回退（set 覆盖旧值）
```

**差距影响：**
- ❌ 不能严格保证找到最优路径
- ❌ 不可达判定基于递归失败而非状态空间穷尽
- ❌ 无法处理需要**状态回退再推进**的复杂链路
- ❌ 无法支持 What-if 分析（需要搜索空间探索）
- ❌ 无法支持规则校验（需要死锁/循环检测）

**下一步建议：**
> 从"逆向差分拼装"迁移到"正向状态空间搜索"。这不是优化，是架构范式转变。
> 需要重新定义 Planner 的核心算法：状态图遍历 + 路径搜索（A* / Dijkstra）。

### 4.3 核心差距2：目标模型 — 状态快照 vs 条件表达式（🔴 P0）

**当前实现：**
- API 要求传入 `current_state_id` + `target_state_id`
- 目标是数据库预定义的**状态快照**（一组固定的 key-value）

**愿景要求：**
- 目标 G 是**条件表达式**（如 `洁净状态 > 100`、`模块A-调测情况 = 已调测`）
- 纯 AND 逻辑，不要求精确匹配预定义终态
- 支持部分目标达成（只关心某几个特征）

**差距影响：**
- ❌ 目标输入被绑定到预定义状态对象
- ❌ 无法直接表达条件型目标
- ❌ 无法支持"只要满足这些条件即可"的灵活目标

### 4.4 核心差距3：并行判定 — 前驱集合 vs 效果可交换性（🔴 P0）

**当前实现：**
- `find_parallel_groups()` 仅按"相同 predecessor 集合"分组
- 例：两个无前置依赖的步骤 → 被认为是可并行

**愿景要求：**
- 双层过滤：
  1. 偏序图中无路径（无前置依赖）
  2. **效果可交换性**（共享 key 的操作满足交换律）

**问题场景：**
- 上电和 下电 两个步骤
- 两者都无前置依赖 → 当前系统可能误判为可并行
- 但实际上两者都修改 `电源状态`（都是 `set` 操作）→ 不可交换 → 不可并行

**差距影响：**
- ❌ 可能输出非法的并行组（两个修改同一状态的步骤并行）
- ✅ Scheduler 最终兜底正确（时间重叠检测），但 Planner 阶段不严谨

### 4.5 核心差距4：数值触发 — 步进规划 vs 事件驱动循环（🔴 P0）

**当前实现（numeric Phase 1）：**
- `increment/decrement` 风格的多步推进
- 从当前值逐步到达 exact target（如 0 → 80，步长 20）

**愿景要求（事件驱动循环）：**
```
安装缺口 = 10
  → 执行安装（sub 1）→ 安装缺口 = 9
  → 执行安装（sub 1）→ 安装缺口 = 8
  → ...
  → 安装缺口 = 0 → **事件触发** → 自动插入清洁工序
  → 清洁工序执行（reset 10）→ 安装缺口 = 10
  → 循环继续...
```

**差距影响：**
- 🚧 当前实现是"数值步进规划"
- ❌ 不是需求中的"触发式维护循环"
- ❌ 未建模事件驱动的维护闭环

### 4.6 核心差距5：资源分配 — 单资源 vs 多资源需求（🟡 P1）

**当前实现：**
- `loader.py` 的 `StepData` 只包含一个 `resource_type`
- `_assign_resources()` 对每个任务只分配**第一个**符合条件的资源实例

**愿景要求：**
- 一个工序可能需要**多种资源**（如：技术人员 + 专用工具 + 场地）
- 每种资源有独立数量需求
- 所有资源同时满足才能执行

**差距验证：**
从代码验证：
```python
# loader.py: StepData 只存一个 resource_type
@dataclass
class StepData:
    resource_type: str
    resource_qty: int
    # 只有一个 resource_type，不支持多资源

# solver.py: _assign_resources 只分配一个资源
for task in tasks:
    pool = pools.get(task.resource_type, [])
    for res in pool:
        if _is_resource_free(...):
            task.resources.append({...})  # 只分配一个
            break
```

**差距影响：**
- ⚠️ 无法支持需要多种资源同时参与的复杂工序
- ⚠️ 与目标存在 gap（需求文档明确要求多资源支持）

### 4.7 差距汇总矩阵

| 差距项 | 当前状态 | 愿景要求 | 差距等级 | 本质问题 |
|--------|---------|---------|---------|---------|
| **求解范式** | 逆向差分拼装 | 正向状态空间搜索 | 🔴 最高 | 拓扑问题→路径问题 |
| **目标模型** | state_id 快照 | 条件表达式 G | 🔴 P0 | 静态→动态目标 |
| **并行判定** | 前驱集合分组 | 效果可交换性 | 🔴 P0 | 忽略业务语义 |
| **数值触发** | 步进规划 | 事件驱动循环 | 🔴 P0 | 非闭环建模 |
| **资源分配** | 单资源需求 | 多资源同时满足 | 🟡 P1 | 模型简化 |
| **规则库导入** | 手工 CRUD | Excel 批量导入 | 🟡 P1 | 维护效率 |
| **可解释性** | 无解释信息 | 每步可溯源 | 🟡 P1 | 信任度 |
| **多目标优化** | 单一 makespan | 多目标加权 | 🟡 P1 | 架构缺口 |
| **What-if** | 部分支持 | 秒级参数对比 | 🟡 P1 | 决策支持 |
| **规则校验** | 未开始 | 离线自动诊断 | 🟢 P2 | 质量保证 |
| **异常恢复** | 未开始 | 自动重规划 | 🟢 P3 | 容错能力 |

## 五、下一步该怎么做

### 5.1 第一步：冻结核心语义（V0.4 最高优先级）

**必须先回答四个问题，再谈扩展：**

1. **目标表达语义**：`state_id` vs `条件表达式 G` → 决定了 API 输入模型
2. **效果操作符语义**：`increment/decrement` vs `set/sub/reset` → 决定了状态变迁模型
3. **并行判定语义**：前驱集合 vs 效果可交换性 → 决定了业务正确性
4. **Planner 搜索语义**：逆向拼装 vs 正向搜索 → 决定了架构方向

**建议决策：**
- 目标表达：支持 `条件表达式 G`（向后兼容 `state_id`）
- 效果操作符：迁移到 `set/sub/reset` 最小集
- 并行判定：新增效果可交换性过滤层
- Planner 搜索：冻结当前实现，同步启动正向搜索预研

### 5.2 第二步：Planner 架构升级（V0.5-V0.6）

**核心工作：从"逆向拼装"到"正向搜索"**

这不是优化，是**范式转变**：

| 维度 | 逆向拼装 | 正向搜索 |
|------|---------|---------|
| 起点 | 目标状态 G | 当前状态 s₀ |
| 推进方式 | 找能产生所需 effect 的工序 | 应用 effect 推进状态 |
| 状态管理 | 静态差分 | 动态状态图 |
| 循环处理 | 简单 DFS 环检测 | 已访问集合去重 |
| 最优保证 | 无 | 有（A* / Dijkstra）|
| 长链路支持 | 弱 | 强 |
| 状态回退 | 困难 | 自然支持 |

**实现路径：**
1. 定义状态图数据结构（节点=状态，边=工序）
2. 实现状态 effect 应用（返回新状态副本）
3. 实现正向搜索（BFS / A* / Dijkstra）
4. 与现有 Scheduler 对接（输出仍然是 RAG）

### 5.3 第三步：补齐周边能力（V0.7-V0.8）

| 能力 | 工作 | 复杂度 |
|------|------|--------|
| 多资源需求 | 扩展 StepData + CP-SAT cumulative 约束 | 中 |
| 数值事件触发 | 建模 sub→归零→触发→reset 闭环 | 高 |
| 求解可解释性 | 每步记录"为什么选这个工序" | 低 |
| Excel 导入 | dry-run + strict_upsert | 中 |
| What-if 对比 | 缓存搜索结果 + 差异分析 | 中 |
| 规则校验 | 死锁/冗余/循环检测 | 高 |

### 5.4 长期愿景（V1.0+）

| 方向 | 当前 | 目标 |
|------|------|------|
| 规模 | 单机台 | 多机台协同 |
| 集成 | 独立系统 | MES/ERP 深度集成 |
| 实时 | 离线排程 | 实时追踪 + 动态调整 |
| 鲁棒 | 确定性排程 | 不确定性建模 |

**V1.0 愿景：**
> 成为复杂装备集成领域的标准计划求解平台，实现从"人驱动排程"到"系统推荐 + 人工确认"的范式转变。
