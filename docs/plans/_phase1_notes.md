## 一、业务场景（4个）

### 场景1: 常规排程 — 从当前进度到目标的最优活动集

**触发时机**：每日生产排程前、每班次开工前、或现场进度推进到关键节点时。

**典型输入**：
- 起点状态 s₀：一组 key-value 对，如 `模块A-安装情况=已安装`、`电源状态=下电`、`安装缺口=2`
- 目标条件 G：基于 key 的逻辑表达式（纯 AND），如 `模块A-调测情况=已调测`、`电源状态=上电`

**期望输出**：
- 候选活动集（通常 ≤70 个）
- 偏序依赖图（活动间前置关系）
- 可并行活动组（基于前置依赖 + 效果可交换性）
- 数值触发规则（路径中由 sub/reset 自动触发的重复活动）
- 线性参考路径（状态序列 + 活动序列）
- 不可达时明确返回"从当前起点到目标不可达"

**核心需求**（原文）：
> "秒级响应，自动处理触发，主线自然涌现，通用活动兼容，结果可解释。"

**示例特征**：
- 上电/下电/再上电反复出现（由前置约束网络自然决定，非预设）
- 安装缺口归零 → 自动触发清洁 → reset 回阈值（数值触发自涌现）
- `set` 覆盖式切换实现安装/拆卸/上下电/建真空/破真空

---

### 场景2: What-if 预演 — 参数变更的影响分析

**触发时机**：
- 工艺优化讨论（清洁阈值从10改为8会怎样？）
- 模板库扩展（新增D模块调测后路径如何变化？）
- 权重调整（提高调测权重是否会避开高成本方案？）

**典型输入**：
- s₀ 和 G 保持不变
- 参数变更：sub幅度变化、新增模板、权重调整、新增活动等

**期望输出**：
- 新旧方案对比表（活动集差异、步数变化、关键路径变化）
- 敏感性结论（如"sub幅度从1→2，清洁次数-1，总步数-1"）
- 可接受近似，不要求每次给出绝对最优解

**核心需求**：
- 单次 What-if 数秒完成
- 差异可视化
- 参数敏感性可量化

---

### 场景3: 工艺规则校验 — 模板库健康度检查

**触发时机**：
- 新增活动模板后验证冲突
- 修改前置条件后验证死锁
- 定期维护检查冗余/循环风险

**典型输入**：
- 完整状态集 S（所有 key 值域笛卡尔积）
- 完整转移函数 T（所有活动效果列表）
- 测试用起点-目标对

**期望输出**：
- 死锁检测报告（孤立状态）
- 冗余活动报告（任何可达路径都不会使用的活动）
- 循环风险报告（sub幅度为0、无前置约束来回切换等）
- 前置条件一致性（矛盾前置检测）
- 效果可交换性冲突（被错误放入同一并行组的冲突对）

**核心需求**：
- 离线分析，可接受分钟级
- 诊断级输出（指出具体活动/key/前置条件）
- 可批量执行

---

### 场景4: 异常恢复 — 起点状态更新后的重规划

**触发时机**：
- 模块返工（质检发现偏差，外部系统更新状态为待调测/未安装）
- 模块替换（损坏模块重置为初始值）
- 数值状态异常（外部 reset 更新安装缺口）
- 切换型状态变更（上电↔下电、建真空↔破真空）

**当前状态**：本版本暂不涉及（P3）。

> "Planner 天然支持从任意给定起点状态重新搜索，异常恢复只需外部系统更新 s₀ 后重新调用 Planner。"

**未来扩展**：
- 状态回退规则（哪些活动可撤销、连带影响）
- 新旧路径差异分析（标记返工/重做部分）
- 快速重算优化（利用上次搜索缓存加速）

## 二、需求优先级（P0-P3）

### P0 — 核心必备

| 需求 | 场景 | 验收标准 |
|------|------|----------|
| 最小代价路径求解 + 条件满足型目标 + 效果触发 | 场景1 | 秒级响应，路径≤70步，自动处理sub/reset触发 |
| 不可达判定 + 路径可解释输出 | 场景1、3 | 不可达时明确返回，每步状态变化可溯源 |
| 效果可交换性并行验证 | 场景1 | 可并行组内共享key时操作可交换，无set冲突 |

|------|------|----------|

| What-if 参数对比 | 场景2 | 参数变更后秒级~十秒级给出新旧方案对比 |

| 需求 | 场景 | 验收标准 |
|------|------|----------|

| 需求 | 场景 | 验收标准 |

## 四、系统愿景与定位

### 一句话定位

> **"规则驱动的状态空间求解引擎 + 计划师操作界面"**
>
> — ANCHOR.md 系统定位原文

完整表述：
> "给定机台的起点状态、目标状态、工序规则库和资源约束，自动推导合法工序路径（RAG）并生成最优排程（CP-SAT），支持计划师对阻塞情况进行动态重排。"

### 5条设计原则如何支撑"减少人工依赖"

| 原则 | 如何减少人工依赖 |
|------|-----------------|
| **原则1：规则内置，数据驱动** | "所有业务知识在规则库，引擎不含业务逻辑。新增工序类型 = 往数据库加数据，不改代码。" → 工艺变更无需改代码 |
| **原则2：模块解耦，接口稳定** | 核心模块只通过数据结构通信，任一模块可独立替换 → 升级替换不影响整体 |
| **原则3：策略模式，注册优于修改** | "新增Operator/Effect/Objective → 注册新类。主流程代码不因扩展而修改。" → 扩展零侵入 |
| **原则4：零侵入扩展** | "新参数必须有默认值，不传时行为与上版本完全一致。" → 升级不破坏现有流程 |
| **原则5：阻塞语义不侵入RAGBuilder** | "阻塞 = 往current_state注入blockage_reason。RAGBuilder只做通用规则匹配，维修序列是推导的自然结果。" → 阻塞处理无需特殊代码逻辑 |

### "明确不在范围内"清单

来自 ANCHOR.md §明确不在范围内（锁定）：

- ❌ 多项目隔离
- ❌ 角色权限管理
- ❌ 跨机台资源调配
- ❌ 实时执行状态追踪（步骤级别）
- ❌ 外部系统推送阻塞信号
- ❌ 执行中阻塞（进行中被中断）
- ❌ 工序时长不确定性建模（鲁棒排程）
- ❌ 技能匹配约束

### 版本路线图

来自 ANCHOR.md §版本路线图：

```
V0.1 ✅ 基础求解链路（状态推导RAG + CP-SAT排程 + CRUD + 前端）
V0.2 ← 当前：阻塞处理 + 架构升级（RuleEvaluator/类型系统/objectives数组化）
V0.3    求解可解释性深化 + 多目标优化 + 工序组 + A*搜索
V1.0    规则库规模化 + Deadline约束 + 历史阻塞模式库 + 外部集成接口
```

**注意**：solver_requirements_summary.md 中将当前版本标记为"已完成数值型状态规划 Phase 1"，这与 ANCHOR.md 中的 V0.3 规划存在语义差异。实际上 gap_report.md 指出当前系统约40%-50%基础能力框架已具备，但距离系统化Planner能力仍有实质性架构差距。

## 五、业务场景到系统能力映射

```
| 业务场景 | 系统模块 | 当前支持 | 仍需人工介入 |
|----------|----------|----------|--------------|
| 常规排程 | Planner (search.py) | delta匹配+依赖补齐；numeric重复步骤实例化；基础不可达判定 | 目标仍通过target_state_id输入（非条件集合G）；代价非最小路径搜索；数值触发非事件驱动语义 |
| 常规排程 | Scheduler (CP-SAT) | 基于precedence与资源约束排程；parallel_groups输出 | 资源建模MVP级别（仅取首个required resource）；效果可交换性未参与并行判定 |
| What-if | API/UI | 版本链+diff展示+blockage replan | 无通用参数注入入口；无参数敏感性输出；非系统化what-if框架 |
| 工艺校验 | （空缺） | 无专用模块 | 全部人工：死锁/冗余/循环/效果冲突均需人工检查 |
| 异常恢复 | Planner | 理论上支持任意s₀重搜索 | 状态回退规则、新旧路径差异分析、快速重算优化均未实现 |
```

### 各场景下"减少人工依赖"空间量化

| 场景 | 当前人工介入环节 | 系统可自动化空间 |
|------|-----------------|-----------------|
| 常规排程 | ① 目标状态需预定义（非条件表达式输入）<br>② 数值触发活动（清洁）插入点需人工确认<br>③ 并行组需人工复核安全性 | ① 条件集合目标直接输入 → 消除目标预定义工作量<br>② sub/reset事件驱动自动插入 → 消除人工计算触发点<br>③ 效果可交换性自动过滤 → 消除人工并行安全复核 |
| What-if | ① 参数变更后手动对比多版本<br>② 敏感性结论人工推导 | ① 自动新旧方案对比表 → 消除手动对比<br>② 参数敏感性自动量化 → 消除人工推导 |
| 工艺校验 | ① 死锁/冗余/循环全靠人工审查规则库<br>② 效果冲突人工检查 | ① 自动化诊断报告 → 将人工审查转为自动化批量检测<br>② 诊断级输出定位具体问题 → 大幅降低排查时间 |
| 异常恢复 | ① 状态更新后人工重规划<br>② 返工范围人工判断 | ① 自动重规划 → 消除人工重跑<br>② 新旧路径差异自动标记 → 快速定位返工范围 |

## 六、关键发现（供后续 Phase 引用）

### 发现1：Planner 核心求解范式与需求定义存在根本性差距

> "当前 Planner 仍是'工程化规则拼装器'，不是'完整最小代价路径搜索器'。"

- 当前：delta 匹配 + precondition/provider 递归补齐
- 需求：从 s₀ 到目标条件集合 G 的最小代价可达路径搜索
- 影响：不能严格保证全局最小代价；不可达判定基于递归失败而非状态空间穷尽

### 发现2：目标模型顶层语义尚未对齐

- 当前 API 要求 `current_state_id` + `target_state_id`（数据库预定义状态快照）
- 需求定义目标 G 应为条件表达式（如 `洁净状态 > 100`），纯 AND 逻辑
- 这导致无法直接表达条件型目标，目标输入被绑定到预定义状态对象

### 发现3：数值触发规则语义差距

- 当前 numeric 实现：`increment/decrement` 风格的 exact target 多步推进
- 需求定义：`sub` 逐步下降 → 归零事件 → 自动触发关联活动 → `reset` 恢复阈值
- 差距报告结论："当前 numeric 更像'数值步进规划'，不是需求中的'触发式维护循环'"

### 发现4：并行判定缺少"效果可交换性"兜底过滤层

- 当前并行信息：Planner `find_parallel_groups` 按前驱集合相同分组 + Scheduler 按时间区间重叠
- 需求要求双层：① 偏序图无路径 ② 共享 key 操作可交换
- 缺失导致：典型冲突场景（如上电+下电共享 `电源状态` 且都是 `set`）无法被严格过滤

### 发现5：效果操作符最小集尚未对齐

- 需求定义最小集：`set` / `sub` / `reset`
- 当前实现：`set` / `increment` / `decrement`
- 缺失 `reset` 导致无法原生建模"归零后触发并恢复阈值"的核心机制

### 发现6：阻塞设计演进方向已明确（方案二）

> 推荐采用"活动级 readiness 门禁建模"：
> - `blockage_reason`：描述阻塞原因，触发维修规则
> - readiness 特征：描述活动是否恢复可执行
> - repair 活动通过 effect 恢复 readiness
> - blocked 活动通过 precondition 依赖 readiness

- 短期：修复单阻塞并行问题（补齐恢复型 precondition）
- 中期：引入活动级 readiness 特征
- 长期：扩展 API 支持多阻塞列表输入

### 发现7：当前系统能力覆盖约40%-50%

来自 gap_report.md 结论：
> "已具备约40%到50%的基础能力框架，已完成部分关键底座，但距离需求文档描述的系统化 Planner 能力仍有实质性架构差距。"

### 发现8：四层语义必须先冻结再扩展

来自 gap_report.md 建议：
> "不建议直接在现有行为上继续局部打补丁，而应先冻结：目标表达语义、效果操作符语义、并行判定语义、Planner搜索语义。"
> "在这四项冻结之后，再展开 What-if、规则校验、解释性深化，会更稳妥。"
