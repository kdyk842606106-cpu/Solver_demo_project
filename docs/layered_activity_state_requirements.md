# 分层活动与状态模型需求

> 状态：V0.3 当前有效
> 更新：2026-07-28
> 替代范围：原 Scope Guard、维护意图和活动包求解继承设计

## 1. 目标

系统要维护一份人机可共读、可求解、可版本化的设备能力知识图。

核心问题是：

```text
设备当前有哪些状态事实？
为了达到目标状态，哪些原子活动可执行？
这些活动需要哪些输入状态，会产生哪些输出状态？
```

状态包和活动包提供知识组织与复用；求解器只消费 canonical 状态事实、原子活动及其规则。

## 2. 当前领域模型

```text
状态包 ── StateNodeReference ──> 原子状态本体
活动包 ── ActivityPackageAtomicRef ──> 原子活动本体
原子状态 ── input ──> 原子活动 ── output ──> 原子状态
原子活动 ── OpRule ──> 前置、效果、时长和资源需求
```

### 2.1 状态

- `StateNode(state_kind=aggregate)` 是状态包；
- 非 aggregate `StateNode` 是原子状态本体；
- 原子状态保存状态维度、运算符和目标值；
- 原子状态 `parent_id` 必须为空；
- 原子状态进入状态包只能创建 `StateNodeReference`；
- 包到子包继续使用 `StateNode.parent_id` 主层级。

### 2.2 活动

- `ActivityNode(level 1/2)` 是活动包；
- `AtomicActivity` 是可被求解器选择的原子活动本体；
- 原子活动进入活动包只能创建 `ActivityPackageAtomicRef`；
- 活动包到子活动包继续使用 `ActivityNode.parent_id`；
- 活动包不拥有原子活动，也不提供求解前置条件；
- `ActivityNode(level=3)` 只读兼容，不再新增。

### 2.3 状态绑定

`ActivityStateBinding` 只以 canonical 本体为端点：

- `input`：执行原子活动必须满足的状态；
- `output`：执行原子活动后达成的状态；
- 同一个绑定的活动端点、状态端点和角色创建后不可原地替换；
- 改变端点或角色必须删除旧关系并创建新关系。

状态包绑定可使用覆盖快照表达“当前包内哪些原子状态被该绑定覆盖”，但其执行端始终是原子活动，不是活动包。

## 3. 本体和引用的边界

| 信息 | 本体 | 引用 |
|---|---:|---:|
| 名称、编码、说明 | 是 | 否 |
| 状态事实或活动能力 | 是 | 否 |
| 规则和状态绑定 | 是 | 否 |
| 所属包 | 否 | 是 |
| 包内排序、启用 | 否 | 是 |
| 包内别名和展示信息 | 否 | 可选 |
| 包内画布位置 | 否 | 是 |

判断原则：离开某个包后仍然成立的信息属于本体；只有进入该包后才成立的信息属于引用。

## 4. 身份和版本

当前数据库内的稳定身份：

- 状态本体：`StateNode.id`；
- 活动本体：`AtomicActivity.id`；
- 状态引用：`StateNodeReference.id`；
- 活动引用：`ActivityPackageAtomicRef.id`；
- 状态绑定：`ActivityStateBinding.id`。

名称和编码可修改，不改变身份。跨实例、跨数据库的稳定业务 key 和 Merkle 内容寻址属于后续版本仓库，不在本需求内。

## 5. 目标状态展开

求解请求可选择一个或多个状态包或原子状态。

解析器必须：

1. 沿状态包主层级和 `StateNodeReference` 展开；
2. 只把启用的原子状态转换为 goal facts；
3. 按 canonical 状态 ID 去重；
4. 检测同一状态维度的冲突目标值；
5. 保留来源路径用于人员解释，但不把 display ID 当作业务身份。

## 6. 有效模型解析

求解预检和正式求解必须调用同一个有效模型解析器。

输入：

- 设备类型；
- 目标状态范围或直接 goal facts；
- 明确的 canonical 原子活动范围；
- `include_inactive` 等审计选项。

输出：

- canonical goal facts；
- 去重后的候选 `AtomicActivity`；
- 每个候选的有效 `OpRule`；
- 原子活动 `input/output` 绑定；
- 结构健康和阻塞诊断；
- `effective_model_version`、摘要和必要快照。

活动包筛选只在请求边界解析一次，随后只传递 canonical 原子活动 ID。活动包层级、引用顺序、第一条引用或引用启停不能成为隐式求解语义。

## 7. Planner 需求

Planner 必须：

- 根据 goal facts 选择最小必要原子活动集合；
- 使用原子活动自己的规则前置和效果；
- 支持多个目标联合求解；
- 对同一 canonical 原子活动的多个显示引用只计算一次；
- 检测不可达目标、冲突目标、缺少 provider 和循环依赖；
- 不读取活动包级历史绑定或 Scope Guard。

当多个不同原子活动都能提供同一事实时，健康检查可提示多个 provider，但同一本体多引用不得误报。

## 8. Scheduler 需求

Scheduler 只排 Planner 生成的 canonical 原子活动实例。

- 不把活动包作为排程任务；
- 不从“第一条活动包引用”推断主分组；
- 活动包移动、改名、换父级或成员调整不能改变活动持续时间、资源需求和前置关系；
- 连续性优化只能使用明确、稳定的调度字段，不得恢复隐式包所有权。

多包复用时如何定义连续性分组属于后续专项，本需求保持无隐式主引用。

## 9. 历史求解重放

每次求解保存：

- 当次 `effective_model_version`；
- 人员可读摘要；
- goal facts、候选活动和有效规则的必要快照；
- 实际计划和排程结果。

历史回放优先读取保存快照，不用当前数据库重新解析旧请求。这样，本体改名、布局调整、活动包重组或规则升级不会改变过去那次求解的含义。

## 10. Scope Guard 日落

Scope Guard 不再是当前有效模型的一部分。

- 停止新增、编辑、删除、复制和导入；
- expansion、health、solver precheck、layered solve 和 Scheduler 均不读取；
- 不再通过活动包路径继承公共前置条件；
- 历史表只读保留用于审计；
- 不自动转换为原子活动绑定；
- 当前发布门禁要求两张历史表均为零。

若存在真实公共准入条件，应由业务人员确认后，为每个受影响的原子活动建立明确 `input` 状态绑定。

当前审计为零，因此 TICKET-097 不执行 Scope Guard 数据库迁移。其他环境一旦非零，发布立即停止并另开数据决策。

## 11. 活动包历史绑定日落

历史 `context_input`、`declared_output`：

- 禁止新增和编辑；
- 默认不进入网络图、有效模型或求解；
- 只通过审计接口读取；
- 不自动转换为原子活动 `input/output`，因为活动包范围可能包含多个语义不同的原子活动。

## 12. 维护意图状态

原“维护意图模板/维护联合求解”产品方向已经废弃，不再维护。

- 不继续扩展 `maintenance_intent_template` 语义；
- 不把维护意图加入新有效模型解析器；
- 现存接口或表仅按历史兼容处理；
- 新需求统一表达为明确的目标状态和原子活动能力。

如未来重新启动该方向，必须新建需求并重新评审，不沿用本文之前的 Scope Guard 或固定意图假设。

## 13. 网络图与知识库

Network Editor 只有 `state_transition` 一种业务画布。

- display 引用实例供人员理解包上下文和独立布局；
- canonical ID 供持久化、校验、影响分析和求解；
- 同一本体可多处显示，但知识库存储一次；
- 包关系、成员关系和状态绑定均为有身份的边；
- 求解预检是同一画布的结果面板，不是另一种图投影。

旧 `outline`、`implementation`、`solver_ready` 参数在兼容窗口内归一化为 `state_transition`，随后删除。

## 14. 安全写入

- 本体在用时禁止删除并返回依赖计数；
- 删除引用不删除本体；
- 引用端点不可更新；
- 跨设备类型引用被拒绝；
- 同一包—本体重复引用被拒绝；
- 统一提交必须全成功或全回滚；
- 场景导入不得创建已日落实体或旧活动层级。

## 15. MVP 非目标

- 不实现完整 Git/Merkle 对象数据库；
- 不实现跨数据库稳定实体 key；
- 不把所有包层级改为任意 DAG；
- 不自动合并分支或自动解决知识冲突；
- 不自动把历史包级语义转换为原子语义；
- 不恢复维护意图或 Scope Guard；
- 不解决多包 Scheduler 连续性归属。

## 16. 验收标准

1. 原子状态和原子活动只能通过引用进入包；
2. 同一本体多引用可独立布局，改名同步且身份不变；
3. 删除引用不删本体，在用本体不可删除；
4. Network Editor 只提供完整状态转移画布；
5. 活动包只管理和筛选，不成为执行节点；
6. 预检与正式求解使用同一 canonical 有效模型；
7. 多引用不会重复生成候选或计划任务；
8. 历史包级绑定和 Scope Guard 不进入当前模型；
9. 每次求解保存模型版本、摘要和必要快照；
10. 真实 PostgreSQL 迁移、全量后端、前端构建和 Chromium 验收全部通过后才能发布。
