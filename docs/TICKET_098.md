## Goal

在 TICKET-097 已冻结的状态/活动本体—引用语义之上，实现“机台类型基线 + 机台实例”的知识库与版本变更管理 MVP：

- 机台类型维护可复用的能力、工艺和配置基线；
- 机台实例代表具体集成设备，并冻结到指定基线版本；
- 正式版本采用稳定身份、内容寻址、完整 Manifest 和不可变 Revision；
- 实例可以选择性回写变化到基线，也可以通过三方合并升级到新基线；
- 预检、正式求解和历史重放使用同一有效模型解析入口；
- 前端按“基础配置 → 模型构建 → 版本管理”组织知识维护工作流；
- 求解继续作为独立主页面，只读取正式实例版本和当次运行时输入。

## Locked MVP scope

### 业务语义

- 只实现机台类型基线主线和机台实例头版本，不实现命名分支。
- 实例版本是逻辑完整模型；冻结基线用于来源、比较、回写和升级。
- 改名不改变 `entity_key`；关系端点或角色变化按删除旧关系和新增新关系处理。
- 内容相同的对象只保存一次；未变化内容继续复用。
- 活动包只引用和管理原子活动，不参与求解。
- Scope Guard、维护意图和虚拟活动不进入现行模型、界面或求解。
- Network Editor 只保留完整 `state_transition` 视图。
- 当前状态、目标状态、临时资源可用性和求解开始时间属于运行时输入，不进入知识版本。

### 前端范围

- 顶部主入口为“机台知识库”和“求解”。
- 机台知识库只有“基础配置、模型构建、版本管理”三个二级页面。
- 基础配置和模型构建共享浏览器会话草稿。
- 正式提交使用 `expected_head_revision_id` 和 `idempotency_key`。
- 历史版本只读；恢复历史内容必须创建新草稿和新 Revision。
- 版本管理提供比较、引用、部分回写和实例升级。
- 大型对象树和差异列表使用虚拟滚动；状态转移图遵守首屏与全量限制。

### 后端范围

- `canonical-json/v1`、稳定身份、内容对象、Manifest、Revision 和 Ref。
- Alembic 015、RevisionStore、兼容投影和 `off → shadow → enforced` 切换。
- 范围创建、读取、验证、提交、差异、引用、回写、升级和重放 API。
- `effective-model/v2` 是知识版本求解的唯一正式解析结果。
- 历史求解保存知识 Revision、有效模型摘要、哈希和必要快照。

## Phase gates

每个实现阶段必须同时满足：

- 对应领域或前端纯逻辑测试通过；
- API 契约测试和错误码映射通过；
- 相关真实浏览器工作流通过；
- 不破坏 TICKET-097 的单一状态转移图和本体—引用语义；
- 需要数据库证据的阶段必须使用 PostgreSQL 副本，不以 SQLite 或 mock-only 代替；
- `shadow` 结果未达到接受基线前不得进入 `enforced`；
- 前端尚未全部切换到知识 Commit 前不得禁止旧写接口；
- 生产切换必须另行确认，不由计划或测试通过自动触发。

## Out of scope

- 命名分支、多人协作评审流和远程分支同步。
- Merkle Tree；MVP 使用扁平 Manifest，但必须通过 RevisionStore 隔离未来替换。
- 服务端长期草稿、离线多端草稿同步和实时协同编辑。
- 复杂嵌套 JSON 或数组的逐元素自动合并。
- 自动把实例全部变化回写基线。
- 跨机台类型合并、跨实例资源调度和权限体系。
- 删除历史 Scope Guard、维护意图、虚拟活动或其他 legacy 审计数据。
- 用实例投影覆盖共享机台类型投影。

## Acceptance summary

- 可创建首个机台类型基线和冻结到该基线的具体机台实例。
- 基础配置和模型构建的变化可以跨页面保留，并一次验证、提交为新版本。
- 并发头变化时保留草稿，不提供强制覆盖。
- 历史版本保持不可变且可只读查看、比较、恢复为新草稿。
- 实例部分回写只生成新基线，原实例不变。
- 实例升级生成新实例版本并更新冻结基线，失败时无半成品。
- 求解只使用正式实例 Revision；预检与正式求解的有效模型哈希一致。
- 历史求解能够使用当次知识版本与运行时快照重放，输入不足时给出稳定错误。
- `off`、`shadow` 和 `enforced` 行为符合设计，具备可验证的切换和回滚路径。
