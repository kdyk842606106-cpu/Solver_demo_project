## 一、业务背景

### 1.1 行业领域

泵体机械集成（Pump Body Mechanical Integration）属于重型装备与精密机械装配领域。核心特征：

- **多模块协同**：单个泵体由多个功能模块（A模块、B模块、C模块等）组成，各模块存在物理接口和功能依赖。
- **工序复杂度高**：每个模块涉及安装、调测、测试、清洁、拆卸、维护等多种操作，顺序受工艺规范约束。
- **状态可回退**：模块可拆卸、可返工，状态并非单向累积（如已安装 → 拆卸 → 未安装）。
- **重复性维护动作**：机械安装过程中累积污染物或磨损，达到阈值时必须清洁，动作重复出现。
- **通用切换活动**：上电/下电、建真空/破真空等通用活动在多个模块间共享状态变量。

### 1.2 核心业务矛盾

- **手工编排效率低**：500+ 活动模板、几十个模块、复杂前置依赖，人工编排耗时长且容易遗漏约束。
- **数值再提供规则难处理**："每安装 N 次/每过 T 时间后，后续活动可能需要清洁再提供"这类规则，人工计算容易遗漏插入点。
- **主线与支线边界模糊**：哪些活动必须在主线、哪些可并行或延后，没有明确数学判定标准。
- **状态可回退增加复杂度**：拆卸、返工导致状态不是单向增长，搜索需处理来回切换。

### 1.3 用户画像

| 角色 | 工程师 / 调度员 |
|---|---|
| 核心诉求 | 输入当前现场进度和目标状态，快速获得可执行的最优活动序列 |
| 技术背景 | 熟悉工艺规范和模块状态，不一定熟悉算法或数据结构 |
| 使用频率 | 每日/每班次排程前常规使用，工艺变更时偶尔使用 |
| 对系统期望 | 结果可解释、可溯源，秒级给出方案，不可达时明确告知原因 |

## 二、最终需求定义

### 2.1 问题类型

从预定义的有限状态集 S 中，搜索从初始状态 s₀ 到目标状态集合 G 的最小代价可达路径。

- **状态集 S**：预定义且有限。每个状态是 **key-value 映射**，key 为层级命名（如 `模块A-安装情况`、`电源状态`、`安装缺口`），value 为对应值。
- **转移关系**：活动与状态转移一一对应。每个活动定义一组**效果列表**（对特定 key 执行特定操作），框架查表应用效果得到下一状态。
- **目标 G**：条件满足型判定，基于 key 的逻辑表达式（如 `模块A-安装情况 = 已安装`、`安装缺口 > 0`），纯 AND 逻辑。

**核心架构原则**：
- **状态变量层级命名**：key 按"模块名-维度名"或"全局变量名"组织，如 `模块A-安装情况`、`模块A-调测情况`、`电源状态`。
- **标量枚举为主**：模块各维度为标量枚举值（单选，互斥），如 `模块A-安装情况` ∈ {未安装, 已安装}。
- **操作符最小集**：`set`（赋值覆盖）、`sub`（算术减）、`reset`（重置为指定值）。
- **框架不预设业务语义**：`set` 在 `模块A-安装情况` 上表现为安装/拆卸切换，在 `电源状态` 上表现为上电/下电切换——行为由值域定义和活动配置自涌现。

### 2.2 输入输出规格

**输入**：
- 初始状态 s₀：一组 **key-value 对**，描述当前现场各状态变量值。例如 `模块A-安装情况=已安装`、`电源状态=上电`、`安装缺口=7`。
- 目标判定条件 G：一组基于 key 的逻辑表达式（如 `模块A-调测情况 = 已调测`、`洁净状态 > 100`），纯 AND 逻辑。

**输出**：
- 候选活动集：路径中出现的所有活动（通常 ≤70 个）。
- 偏序依赖图：活动之间的前置依赖关系。
- 可并行活动组：基于**前置依赖 + 效果可交换性**识别的合法并行活动子集。
- 数值触发 / 再提供规则：路径中由前序活动 effect 导致后续活动前置条件失效时，自动插入可重新提供该条件的重复活动（如清洁、重新上电）及其触发原因。
- 线性参考路径：供人工审查和 Scheduler 调用的状态序列 + 活动序列。

> 需求澄清（2026-06-02）：重复清洁不采用独立的“全局阈值触发器”语义。需要洁净环境的后续活动必须显式声明前置条件（如 `洁净度 > 30`）；当前序机械活动的 effect 使该前置条件不再满足时，Planner 应通过 effect-driven re-provider 机制自发插入清洁活动。重复上下电与重复清洁统一为“后续 consumer 的 support fact 被破坏后重新提供”的 POP 问题。

**不可达时**：
- 明确返回"从当前起点到目标不可达"，不陷入无限搜索。

### 2.3 核心约束参数

| 约束项 | 参数值 | 说明 |
|---|---|---|
| 活动模板库规模 | 500+ | 按"模块+操作"定义，无泛化活动 |
| 单次求解涉及活动数 | ≤70 | 实际路径中只会用到模板库子集 |
| 典型路径长度 | ~50 步 | 从起点到目标的状态转移步数 |
| 主线活动占比 | ≥70% | 主线由前置约束自然涌现，非人工定义 |
| 数值型阈值上限 | ≤20 | 安装/时间缺口压缩至 [0, 阈值] 区间 |
| 起点-终点关系 | 单起点 → 单终点 | 每次求解一条路径 |
| 状态结构 | key-value 映射，key 层级命名 | 如 `模块A-安装情况`、`电源状态` |
| 模块状态维度 | 标量枚举（单选，互斥） | 每个维度一个值，安装/拆卸/调测等切换 |
| 状态变量值域 | 有限离散域 | 每个 key 值域预定义且有限，状态空间有界 |
| 效果操作符 | set / sub / reset | 最小操作集，行为由配置自涌现 |
| 目标条件逻辑 | 纯 AND | 所有条件必须同时满足，无 OR 分支 |
| 并行判定依据 | 前置依赖 + 效果可交换性 | 偏序无路径 + 共享 key 操作可交换 |
| 代价单位 | 统一权重 | 反映复杂度/风险/优先级，不涉及工时/人天 |
| 目标状态规模 | 差值驱动 | 全量目标几百个条件，实际差值几十个，起点通常已接近目标 |

### 2.4 关键业务规则

**规则 1：活动效果自涌现业务行为**

每个活动定义一组效果列表，每项效果是对某个 key 的操作。框架只执行操作，不预设业务语义。

- **`set` 操作**：赋值覆盖，旧值被替换。在标量枚举 key 上表现为切换（安装/拆卸、上电/下电）。
- **`sub` 操作**：算术减。在数值 key 上表现为缺口递减（安装缺口 -= 1）。
- **`reset` 操作**：重置为指定值。在数值 key 上表现为归零后恢复阈值（安装缺口 reset 10）。

业务规则不硬编码在框架中，作为活动模板的配置数据存在。

**规则 2：状态可回退**

框架不做"不可逆"假设。`set` 可覆盖旧值，允许状态来回切换：
- `模块A-安装情况 set 已安装` → 安装
- `模块A-安装情况 set 未安装` → 拆卸回退
- `电源状态 set 上电` → 上电
- `电源状态 set 下电` → 下电

**规则 3：前置约束决定可达性**

每个活动有前置条件（基于 key 的逻辑表达式，如 `模块A-安装情况 = 已安装`），不满足则不可执行。

**规则 4：目标条件满足即终止**

搜索到达的状态满足目标条件（基于 key 的逻辑表达式，允许属性超出目标定义），即判定达成，不要求精确匹配预定义终态。

**规则 5：效果可交换性决定并行（兜底层）**

两个活动可并行，需同时满足：
1. **偏序图中无路径**（无前置依赖）—— 处理"谁必须在谁之前"。
2. **共享 key 上的操作可交换** —— 处理"谁和谁不能同时做（即使互不依赖）"。

**两层过滤的分工**：

| 过滤层 | 判定依据 | 典型场景 | 示例 |
|---|---|---|---|
| **偏序图过滤** | 前置条件构成的有向路径 | 上电 → 下电（下电前置要求上电） | 下电必须在之后，偏序图已有边，无需效果检查 |
| **效果可交换性过滤** | 共享 key 的操作是否满足交换律 | 两个独立上电活动（前置都为空） | 偏序图无边，但共享 `电源状态` 且都是 `set`，不可并行 |

**效果可交换性判定矩阵**：

| 操作组合 | 共享 key | 可并行？ | 原因 |
|---|---|---|---|
| `set` + `set` | 是 | **否** | 覆盖不交换，结果取决于执行顺序 |
| `set` + `sub` | 是 | **否** | 覆盖 vs 算术不交换 |
| `set` + `reset` | 是 | **否** | 覆盖 vs 重置不交换 |
| `sub` + `sub` | 是 | **是** | 减法交换律，`a-d₁-d₂ = a-d₂-d₁` |
| `sub` + `reset` | 是 | **否** | 算术 vs 覆盖不交换 |
| `reset` + `reset` | 是 | **否** | 重置为不同值不交换 |

**关键原则**：`set` 与任何写操作（`set`/`sub`/`reset`）共享 key 时都不可并行。`sub` + `sub` 可并行。

## 三、使用场景详解

### 场景 1：常规排程 — 从当前进度到目标的最优活动集

**触发时机**

每日生产排程前、每班次开工前、或现场进度推进到关键节点时。

**典型输入示例**

```
起点状态 s₀（key-value 映射）：
  模块A-安装情况 = 已安装
  模块A-调测情况 = 待调测
  模块B-安装情况 = 已安装
  模块B-调测情况 = 已调测
  电源状态 = 下电
  真空状态 = 破真空
  安装缺口 = 2        // 后续需要安装缺口 > 0 的活动可能在缺口耗尽后需要清洁再提供

目标条件 G（key 的逻辑表达式）：
  模块A-安装情况 = 已安装
  模块A-调测情况 = 已调测
  模块B-安装情况 = 已安装
  模块B-调测情况 = 已调测
  电源状态 = 上电
  真空状态 = 建真空
```

**状态转移示例（效果自涌现）**

```
执行 "模块A-调测"
  前置: 模块A-安装情况 = 已安装 AND 电源状态 = 上电
  效果: (模块A-调测情况, set, 已调测)

执行 "模块A-拆卸"
  前置: 无
  效果: (模块A-安装情况, set, 未安装)

执行 "上电"
  前置: 无
  效果: (电源状态, set, 上电)

执行 "B模块安装"
  前置: 无
  效果: (模块B-安装情况, set, 已安装) + (安装缺口, sub, 1)

执行 "清洁"（用于重新提供后续活动所需的安装缺口/洁净度前置条件）
  效果: (安装缺口, reset, 10)
```

**自涌现路径示例**

```
步1  B模块安装     模块B-安装情况=已安装    安装缺口: 2→1
步2  上电           电源状态=上电           —
步3  A模块调测     模块A-调测情况=已调测    —
步4  下电           电源状态=下电           —    // 建真空前置要求下电
步5  建真空         真空状态=建真空         —
步6  B模块调测     模块B-调测情况=已调测    —    // 依赖建真空完成
步7  A模块安装     模块A-安装情况=已安装    安装缺口: 1→0 → 后续前置条件失效
步8  [清洁]         —                      安装缺口: 0→10
步9  上电           电源状态=上电           —    // 重新上电
步10 A模块调测     模块A-调测情况=已调测    —
```

**路径中反复执行的活动**

| 活动 | 执行次数 | 原因 |
|---|---|---|
| **上电** | 2 次 | 步2 为 A调测供电；步4 被迫下电（建真空前置倒逼）；步9 重新上电为 A再调测。 |
| **下电** | 1 次 | 步4 满足建真空前置条件。 |

**上电/下电的位置不是预设的**。步4 下电出现在建真空之前，是因为建真空的前置条件是 `电源状态 = 下电`，偏序图把下电串行在建真空之前。步9 重新上电是因为后续调测要求 `电源状态 = 上电`。这些顺序由前置约束网络自然决定，框架不做任何预设。

**A模块安装触发清洁**。步7 A模块安装导致 `安装缺口` 从 1 减到 0，使后续需要 `安装缺口 > 0` 或 `洁净度 > 阈值` 的活动前置条件不再满足。Planner 应自动寻找可重新提供该 support fact 的活动（如 `清洁`，效果 `安装缺口 reset 10`），并把它插入到触发源活动与后续 consumer 之间。清洁插入位置由前置条件网络和 effect 回放自涌现，不是人工指定的。

**核心需求**

- 秒级响应：单次求解时间不超过几秒。
- 自动处理再提供：由前序 effect 破坏后续前置条件时，自动涌现重复 provider 插入逻辑（如清洁、重新上电）。
- 主线自然涌现：不预定义"必须先做完 A 再做 B"，由前置约束和目标条件共同决定。
- 通用活动兼容：同一框架兼容上电/下电（`set` 切换）、安装/拆卸（`set` 切换）、安装后清洁再提供（`sub`/`reset`），不特例化任何活动。
- 结果可解释：工程师能看懂每一步的状态变化、效果执行、前置判定。

**可并行组提取示例（双层过滤）**

以路径 `步1 B安装 → 步2 上电 → 步3 A调测 → 步4 下电 → 步5 建真空` 为例：

**偏序图过滤（第一层）**：
- 上电 → A调测（A调测前置要求电源=上电）
- 上电 → 下电？**无边**（下电前置为空）
- 下电 → 建真空（建真空前置要求电源=下电）
- B安装 → B调测（B调测前置要求B已安装）

**效果可交换性过滤（第二层，兜底层）**：
- 上电 vs 下电：共享 key=`电源状态`，都是 `set`。偏序图无边，但效果不可交换 → **不可并行**。
- 上电 vs B安装：上电改 `电源状态`，B安装改 `模块B-安装情况` + `安装缺口`。无共享 key → **可并行**。
- 下电 vs A调测：下电改 `电源状态`，A调测改 `模块A-调测情况`。无共享 key → **可并行**。

**最终可并行组**：
- 组1: {B安装, 上电} —— 偏序无边，无共享 key，可并行。
- 组2: {A调测, 下电} —— 偏序无边，无共享 key，可并行（但A调测要求电源=上电，实际上电在步2已执行，A调测在步3已执行，下电在步4，时间上是串行的，这是偏序图已保证的）。

**注意**：上电与下电不可并行，不是由偏序图发现的（下电前置为空，不依赖上电），而是由**效果可交换性**发现的。这是双层过滤的必要性。

### 场景 2：What-if 预演 — 参数变更的影响分析

**触发时机**

- 工艺优化讨论："如果把清洁阈值从 10 改为 8，总活动数会增加多少？"
- 模板库扩展："新增 D模块的调测活动后，整体路径会如何变化？"
- 权重调整："如果提高调测活动的权重，路径会不会避开某些高成本方案？"
- 状态回退策略："如果拆卸权重很高，系统会倾向于返工还是直接推进？"

**典型输入**

```
起点 s₀ 和目标 G：保持不变。
参数变更：
  某安装活动的效果参数：安装缺口 sub 幅度从 1 → 2（每次安装减少 2）
  或：新增 "模块D-调测" 活动模板
  或：拆卸活动权重从 1 → 5
  或：新增 "破真空" 活动模板（效果：真空状态 set 破真空）
```

**期望输出**

- 新旧方案对比表：活动集差异、步数变化、关键路径变化。
- 敏感性结论：参数变动对总步数的影响（如"安装 sub 幅度从 1→2，清洁次数减少 1 次，总步数 -1"）。
- 可接受近似：不要求每次 What-if 都给出绝对最优解，可接受上下界估算。

**核心需求**

- 快速对比：单次 What-if 在数秒内完成。
- 差异可视化：直观看出哪些活动被增删、哪些顺序被调整。
- 参数敏感性：阈值、权重、sub 幅度对路径的影响可量化。

### 场景 3：工艺规则校验 — 模板库健康度检查

**触发时机**

- 新增活动模板后：验证新模板是否与现有模板存在冲突。
- 修改前置条件后：验证是否引入死锁或破坏原有可达路径。
- 定期维护：检查模板库中是否存在冗余活动或循环风险。

**典型输入**

```
完整状态集 S（所有 key 的值域笛卡尔积）
完整转移函数 T（所有活动的效果列表）
一组测试用的起点-目标对（覆盖常见场景）
```

**期望输出**

- **死锁检测报告**：列出从某些起点出发永远无法到达任何目标的状态（孤立状态）。
- **冗余活动报告**：列出在任何可达路径中都不会被使用的活动（无前置活动需要它的效果、或值域设计导致效果不产生实际状态变化）。
- **循环风险报告**：检查是否存在可能导致搜索无限循环的路径（如数值 key 的 `sub` 幅度为 0、或切换型活动无前置约束导致来回切换无进展）。
- **前置条件一致性**：检查是否存在矛盾的前置条件（如 A 要求 B 在前，B 又要求 A 在前）。
- **效果可交换性冲突**：检查是否存在两个活动效果中共享 key 但操作不可交换，且被错误放入同一可并行组的情况。

**核心需求**

- 离线分析：不要求实时，可接受分钟级。
- 诊断级输出：指出具体哪个活动/哪个 key/哪个前置条件导致问题。
- 可批量执行：一次性校验整个模板库。

---

### 场景 4：异常恢复 — 起点状态更新后的重规划（暂不涉及，未来扩展）

**触发时机**

- 某模块返工：模块A已调测，但质检发现安装偏差超标，外部系统通过 `set` 更新 `模块A-调测情况 = 待调测` 或 `模块A-安装情况 = 未安装`。
- 模块替换：模块C损坏，外部系统 `set` 重置为初始值。
- 数值状态异常：外部系统 `reset` 更新安装缺口。
- 切换型状态变更：从"上电"切换为"下电"，或从"建真空"切换为"破真空"。

**当前状态**

本版本暂不涉及。Planner 天然支持"从任意给定起点状态重新搜索"，异常恢复只需外部系统更新 s₀ 后重新调用 Planner。

**未来扩展方向**

- 状态回退规则：定义哪些活动可撤销、撤销后连带影响哪些下游状态。
- 新旧路径差异分析：对比异常前后的路径，标记需要返工/重做的部分。
- 快速重算优化：利用上次搜索缓存，加速从相近起点的重新搜索。

## 四、跨场景通用需求

### 4.1 状态模型需求

| 需求 | 说明 | 关键参数 |
|---|---|---|
| 活动模板库规模 | 预定义的活动总数 | 500+ |
| 单次求解涉及活动数 | 单条路径实际用到的活动 | ≤70 |
| 典型路径长度 | 从起点到目标的状态转移步数 | ~50 步 |
| 主线占比 | 路径中主线活动比例 | ≥70% |
| 状态结构 | key-value 映射，key 层级命名 | 如 `模块A-安装情况`、`电源状态` |
| 模块状态维度 | 标量枚举（单选，互斥） | 每个维度独立 key，安装/拆卸/调测等切换 |
| 状态变量值域 | 有限离散域 | 每个 key 值域预定义且有限，状态空间有界 |
| 效果操作符 | set / sub / reset | 最小操作集，行为由配置自涌现 |
| 阈值上限 | 数值型状态的最大阈值 | ≤20（由值域定义保证） |
| 目标条件逻辑 | 纯 AND | 基于 key 的逻辑表达式，无 OR 分支 |

### 4.2 搜索与路径需求

| 需求 | 说明 |
|---|---|
| 不预定义主线骨架 | 主线/支线不由人工编排，由搜索算法根据前置约束和目标条件自然涌现 |
| 统一单位代价 | 所有活动可比较、可累加，不存在多目标优化 |
| 条件满足型目标 | 目标为条件集合（标量等值 + 数值比较），不要求精确匹配预定义终态 |
| 最小代价路径 | 在所有满足目标的路径中，返回总代价最小的一条 |
| 不可达判定 | 能明确回答"从当前起点到目标不可达" |
| 结果可解释 | 每一步的状态变化、效果执行、前置判定都清晰可追溯 |
| 状态可回退 | 支持拆卸、返工等状态回退操作，`set` 覆盖旧值实现 |

### 4.3 数值再提供需求

| 需求 | 说明 |
|---|---|
| 累积型再提供 | "每安装 X 次/每过 T 时间后，后续活动阈值前置条件可能失效，需要清洁再提供" |
| 事件驱动响应 | 数值 key 因前序 effect 下降到不满足后续活动前置条件时，自动插入可重新提供该条件的活动（效果可含 `reset`） |
| 循环可处理 | 允许安装→清洁→安装的循环出现，不限制循环次数（或限制在合理上界内） |
| 多维度并行 | 安装缺口和时间缺口同时存在，任一维度导致后续前置条件失效都可要求对应 provider |
| 阈值按活动配置 | 需要洁净/缺口余量的后续活动显式配置阈值前置条件；不同活动的 `sub` 幅度和 `reset` 目标值可独立配置 |

### 4.4 效果与并行需求

| 需求 | 说明 |
|---|---|
| 双层并行判定 | 第一层：偏序图过滤（前置依赖决定串行）；第二层：效果可交换性过滤（共享 key 写冲突兜底） |
| 偏序图过滤 | 前置条件构成的有向路径决定"谁必须在谁之前"，如 下电 必须在 上电 之后 |
| 效果可交换性检查 | 偏序图无边时，检查共享 key 的操作是否可交换，如两个独立上电活动不可并行 |
| `set` 互斥 | `set` 与任何写操作（`set`/`sub`/`reset`）共享 key 时不可并行 |
| `sub` 可交换 | 同一数值 key 上的 `sub` + `sub` 可交换，可并行 |
| 标量枚举互斥 | 同一标量枚举 key 上的两个 `set` 不可并行（如两个上电） |

### 4.5 性能与规模需求

| 需求 | 说明 |
|---|---|
| 实时性要求 | 常规排程：秒级；What-if 分析：秒级~十秒级；工艺校验：可接受分钟级 |
| 状态空间可控 | 预定义有限状态集，单次求解访问状态数在 10⁵~10⁶ 量级 |
| 模板库动态扩展 | 支持新增活动模板，但不要求在线实时增删 |
| 目标差值驱动 | 实际搜索深度由起点与目标的差值决定（通常几十个条件），而非全量目标规模 |

## 五、Planner 与 Scheduler 分层边界

| 维度 | Planner（本方案） | Scheduler（外部模块，CP-SAT） |
|---|---|---|
| **核心任务** | 状态空间搜索：找候选活动集、前置依赖、重复活动插入点、参考路径、可并行组 | 资源约束求解：资源冲突识别、时间调度、并行优化 |
| **输入** | s₀、G、转移表、活动属性 | Planner 输出的活动集 + 偏序关系 + 效果可并行组 + 资源需求 |
| **输出** | 活动序列 + 偏序依赖图 + 可并行活动组 + 数值再提供原因 + 参考路径 | 带时间戳的调度方案（谁、何时、用何资源） |
| **代价考量** | 活动权重/步数最小化（反映复杂度/风险/优先级） | 工时、人天、资源利用率、工期最小化 |
| **并行处理** | 识别逻辑上可并行的活动组（前置无依赖 + 效果可交换） | 在资源约束下决定实际并行方案 |
| **数值再提供** | 确定清洁等重复 provider 的插入位置和被修复的前置条件 | 根据实际资源安排清洁的具体执行时间 |
| **状态冲突** | 双层过滤：偏序图过滤前置依赖串行 + 效果可交换性过滤共享 key 写冲突 | 不处理（Planner 已过滤） |
| **异常恢复** | 从给定 s₀ 重新搜索（未来扩展） | 资源重新分配、工期重新计算 |

**协作流程**：

1. Planner 接收 s₀ 和 G，搜索最优路径。
2. Planner 输出：候选活动集 + 偏序图 + **效果可交换性验证后的可并行组** + 数值再提供原因 + 参考路径。
3. Scheduler 接收 Planner 输出，结合资源约束做 CP-SAT 求解。
4. Scheduler 输出：带时间戳的最终调度方案。

## 六、隐性需求与边界

### 6.1 隐性需求

- **路径可解释性**：输出包含每一步的状态变化和可选活动列表，工程师能看懂"为什么先做这个"。
- **增量更新**：现场进度推进时，支持从上次终点状态继续求解（状态变量值直接复用）。
- **容错性**：输入状态与预定义状态集不一致时，系统能归一化处理或报错提示。
- **结果稳定性**：相同输入给出相同输出（确定性），便于对比和复现。
- **效果可交换性验证**：Planner 输出可并行组时，必须保证组内任意两活动的效果操作在共享 key 上可交换。

### 6.2 边界约束（不在本方案范围内）

- **不做人身安全相关的实时控制**：Planner 输出调度建议，不是设备直接控制指令。
- **不涉及多资源竞争调度**：人员分配、设备占用、场地冲突由 Scheduler（CP-SAT）处理。
- **不考虑物料到货延迟等外部不确定性**：输入状态假设为"当前已知真实状态"。
- **不处理异常回退逻辑**：本版本不涉及状态撤销的自动推导，异常恢复由外部系统更新 s₀ 后重新调用 Planner。

## 七、需求优先级

| 优先级 | 需求 | 场景覆盖 | 验收标准 |
|---|---|---|---|
| **P0** | 最小代价路径求解 + 条件满足型目标 + effect-driven re-provider | 场景 1 | 秒级响应，路径 ≤70 步，自动处理 `sub`/`reset` 再提供 |
| **P0** | 不可达判定 + 路径可解释输出 | 场景 1、3 | 不可达时明确返回，路径每一步的状态变化和效果执行可溯源 |
| **P0** | 效果可交换性并行验证 | 场景 1 | 可并行组内任意两活动共享 key 时操作可交换，无 `set` 冲突 |
| **P1** | 并行关系自涌现 + 偏序图输出 | 场景 1 | 输出合法可并行组，供 Scheduler 使用 |
| **P1** | What-if 参数对比 | 场景 2 | 参数变更后秒级~十秒级给出新旧方案对比 |
| **P2** | 工艺规则离线校验 | 场景 3 | 死锁/冗余/循环风险/效果冲突检测，诊断级输出 |
| **P3** | 异常恢复重规划 | 未来扩展 | 状态回退后快速重算，输出新旧差异 |

## 八、待确认或未来细化事项

1. **权重设定规则**：活动权重由谁来设定、如何量化（复杂度评分？风险等级？优先级权重？）。
2. **阈值配置来源**：后续活动的数值阈值前置条件（如安装缺口/洁净度最低值）是工艺固定值还是可调参数？
3. **模块间跨依赖**：是否存在跨模块的前置条件（如"模块B-调测"要求"模块A-调测 = 已调测"）？
4. **目标条件自动生成**：目标状态 G 由工程师手工输入还是从上层系统（ERP/MES）自动下发？
5. **清洁活动的前置条件**：清洁活动是否要求特定状态（如"电源状态 = 上电"）才能执行？
6. **拆卸/返工的代价权重**：拆卸权重是否显著高于正常推进，以避免搜索随意选择返工路径？

## 九、总结

本方案的核心定位是 **Planner 模块**：在明确的分工边界内，解决"从当前状态到目标状态，应该做什么、按什么顺序做"的问题。

**核心设计原则**：
1. **状态结构统一**：key-value 映射，key 层级命名（`模块A-安装情况`），标量枚举为主，数值计数为辅。
2. **操作最小集**：`set` / `sub` / `reset`，无 `add`，无类型区分，业务行为由配置自涌现。
3. **状态可回退**：`set` 覆盖旧值，支持拆卸、返工、上下电切换等来回操作。
4. **并行双重判定**：偏序图无路径 + 效果可交换性（`set` 与任何写冲突，`sub`+`sub` 可交换）。
5. **数值再提供驱动**：前序 effect 使后续活动的数值前置条件失效时，自动插入清洁等重复 provider；`reset` 是清洁类 provider 的恢复效果。
6. **Planner-Scheduler 分层**：Planner 管"做什么、按什么顺序、哪些逻辑上可并行"，Scheduler 管"何时做、用多少资源"。
7. **在约束内秒级响应**：500+ 模板、≤70 步路径、阈值 ≤20、A* 搜索 + 三层剪枝。
