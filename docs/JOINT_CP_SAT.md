# 联合 CP-SAT 求解入口

2026-11-03，TICKET-105。入口位于「多引擎求解」→「运行方式」→「联合 CP-SAT」。同时增加「四引擎对比（含联合 CP-SAT）」；默认仍为原三引擎对比，原 LEGACY / A* / GA 算法和默认搜索参数不变。

该入口直接从完整的共享场景编译可选活动实例、状态因果支持、破坏保护和资源区间，联合决定执行哪些活动、执行次数、执行顺序及时间。它不调用 POP 预先选定任务集，不读取实验答案、见证或提示。已验证的通用编译器已移入 `app/core/joint_cpsat.py`，运行不导入 `experiments`。

## 使用与配置

沿用现有共享场景运行时依赖：`PLANNER_PROJECT_PATH` 指向包含 `planner_experiment` 的 Planner 仓库，默认取当前项目同级的 `planner`。OR-Tools 沿用项目已有依赖。

首次启用需要执行数据库迁移，新增合法引擎标识，不重写历史结果：

```powershell
.venv/Scripts/python.exe -m alembic upgrade head
```

本次开发环境的 `localhost:55150 / solver_db` 无法连接，因此未应用到实际 PostgreSQL；迁移的 PostgreSQL SQL 已检查，独立 SQLite 迁移测试已通过。数据库恢复后执行上述命令并重启后端，前端按既有流程启动或构建。不要把代码验收视为在线服务已经部署。

API 继续使用 `POST /api/v1/planner-runs`，传入现有场景 ID、版本及当前/目标状态：

```json
{
  "scenario_id": "<已有场景ID>",
  "expected_revision": 1,
  "current_state_ids": ["<实际当前状态ID>"],
  "target_state_ids": ["<实际目标状态ID>"],
  "engine": "JOINT_CP_SAT",
  "seed": 11,
  "budget": {"time_limit_seconds": 60}
}
```

`ALL` 仍调用原三引擎；`ALL_WITH_CP_SAT` 显式调用四引擎。产品对比沿用并发调用方式，不等同于正式实验的单核串行公平计时。每个引擎读取隔离的同一快照，结果和快照一起持久化。能力信息见 `GET /api/v1/planner-runs/capabilities`。

联合 CP-SAT 默认使用最多 8 个 CPU 搜索线程和请求种子，首先优化总工期，在同等工期下最小化活动总执行次数；界面的权重仍只作用于旧引擎。它返回通过校验的最佳候选，`max_solutions` 不表示生成多样方案，`transition_limit` 不限制 CP-SAT 搜索分支。输入 `max_steps` 和各活动 `max_instances` 仍是硬执行次数边界，未指定单活动上限时以 `max_steps` 为界。最优/无解证明只覆盖这些边界定义的模型。

预算是有限非负秒数，包含联合模型构建、搜索和候选规范化校验。截止后才完成校验的候选不接收；截止前接受的最佳候选保留。使用协作式截止，某次同步构建/校验及公共结果序列化可能使完整调用略微超时，没有独立进程强制终止机制。前端请求超时随预算延长；界面支持至 3600 秒，默认仍为 5 秒。

## CPU 多线程搜索（2026-11-06）

每个联合求解任务默认使用 `min(8, 可用逻辑 CPU 数)` 个搜索线程；队列同时运行任务数不变。可在启动后端及 worker 前设置环境变量 `PLANNER_JOINT_CP_SAT_WORKERS` 为正整数，设为 `1` 可恢复单线程，超过可用 CPU 数时自动限制。反馈证书验证仍使用单线程。没有使用 GPU。

本次只改变搜索并行度及进度计数处理，不改变业务约束、目标、实例裁剪或已有反馈策略；必做活动强化和因果层级约束继续关闭。回调用可重入锁保护最好方案、下界和进度写入。通过回放的改善方案继续实时上报，数据库及页面沿用 5 秒合并/刷新。

多线程 CP-SAT 的原生响应分支数和冲突数来自第一个子搜索器，不是所有线程总和。因此多线程时不累计来自不同候选回调的计数，只在每轮搜索结束时接收原生响应并跨轮累计；运行中计数可能暂不变化。界面显示实际线程数和“报告分支”，跨线程分支/秒留空，不生成虚假的总速度。详见 [OR-Tools v9.15 响应定义](https://github.com/google/or-tools/blob/v9.15/ortools/sat/cp_model.proto)。

在 16 逻辑 CPU 的本机，以冻结的测试A输入、相同 60 秒预算和种子 11/23/37/53/71，顺序启动独立进程对比 1/4/8 线程；另对种子 53 的每个场景复跑 4/8 线程，共 51 次。每个初始模型哈希均与之前关闭两项强化的单线程基准相同。所有运行均证明最优并通过回放，工期/执行次数分别保持 400/10、1570/14、390/10。

| 场景 | 1 线程总耗时中位数 | 4 线程 | 8 线程 |
|---|---:|---:|---:|
| 正常安装 | 0.821 秒 | 0.239 秒 | 0.254 秒 |
| 物料晚到 | 5.431 秒 | 1.678 秒 | 0.996 秒 |
| 维修恢复 | 11.377 秒 | 2.787 秒 | 1.975 秒 |

8 线程在 15 组主对照中全部快于单线程；4 线程有两组退化。维修恢复种子 53 从 44.479 秒缩短至 1.559 秒，8 线程重复试验为 2.165 秒。并行调度使同一种子的路径也可能变化，这些结果不保证其他输入或机器具有相同加速比。耗时包括候选校验和反馈，不能用跨线程的分支数比值计算加速。

验证包括 262 项相关回归、最终 12 项并行配置/恢复/时间窗测试及前端生产构建。结果保存在 [完整对照报告](validation/MULTICORE_20261106.json)，原始日志位于 `output/multicore-20261106/`；未写入项目配置或运行历史。复现入口为 `scripts/benchmark_multicore.py`、`scripts/report_multicore.py`。

## 本次初始状态与目标驱动的裁剪（2026-11-05）

联合编译器在创建 CP-SAT 变量前应用 `initial_goal_repeat_proof_v3`。使用本次运行快照中的初始、正目标和最终禁止状态，不使用项目默认状态替代用户的本次选择。

预处理按轮执行：

1. 忽略破坏、时间和资源限制，计算宽松可达状态；排除前置状态仍不可达的活动。
2. 从初始状态中扣除剩余活动可能移除的状态，得到确定持久的初始事实。
3. 从全部正目标向后追溯所有产生者与前置条件；同时保留最终禁止状态的所有潜在清除者及其依赖。只有已证明持久的初始事实可以停止追溯。备选产生者不提前择一。
4. 使用独立检查函数核验本轮投影条件：可达集合包含初始状态并对可执行活动的输出闭合；持久事实不会被可达活动移除；删除的可达活动不能提供保留活动/目标仍需要的正事实，也不能清除最终禁止事实。核验通过后才提交本轮缩减，并迭代至集合不再变化。

排除的活动有效实例数为 0。在最后一轮已核验的范围中重新计算产生者和破坏者；满足任一条件的活动有效上限收紧为 1（仍受原输入上限约束）：

- 自身没有状态消耗或删除，且全部输出均不会被剩余活动移除。
- 消耗至少一个没有剩余产生者的转移前置状态，该状态消耗后无法恢复。

其余活动保留原执行次数边界。检查使用解析后的全部状态 ID 语义，包含额外输出、转移、独立删除与旧格式 SET 隐含覆盖。自身输出持久但需要反复删除其他状态的活动不会因此被限制一次。不能证明的恢复机会不会被猜测性删除。

预处理最多使用一秒，并受共享求解截止时间限制。轮次超时或证书核验失败时丢弃未提交轮次，保留上一轮安全范围；若尚无安全轮次则回退全部活动。状态分别记录为 `time_slice_exhausted`、`certificate_rejected`，不据此宣称无解。改变状态的外部事件仍按既有能力检查返回不支持。

裁剪只影响编译器创建的实例；项目、活动业务上限、运行快照、哈希和冻结日历范围不改变。回放继续使用完整原始场景。此保证相对于原输入次数边界，不证明自动启发式上限覆盖无限次恢复，也不进行条件式重复实例约束。

诊断在 `stats.model.occurrence_pruning`：`activity_limits` 给出输入和有效上限，`activity_proofs` / `retained_activities` 给出逐活动依据；`scope_analysis` 保存策略、耗时、完成/回退状态、每轮数量、持久初始状态和被排除活动的原因及轮次。历史记录不会重写。

验证：151 项相关测试通过，其中 32 组小型随机场景用独立状态枚举对照裁剪前后的串行最优结果；还包括四种初始/目标组合、必须二次安装、负目标清除、所有备选产生者、旧格式覆盖、日历/夜班/独占、核验失败和超时回退、API 快照不变。测试A从原始 210 实例/7874 分支，降至 9 实例/10 分支，仍为最优 758 分钟、9 次执行；当前 20 活动 V6 为 625 分钟、20 次执行；复验的 150 活动夜班历史快照为 2831 分钟、150 次执行（该快照与此前 3033 分钟验收运行的输入不同）。三者均为 OPTIMAL、回放 VALID。证据见 `docs/validation/DYNAMIC_OCCURRENCE_PRUNING_20261105.json`。

早期全场景、逐活动静态裁剪的历史对照证据分别保留在 `OCCURRENCE_PRUNING_20261105.json` 和 `SELECTIVE_OCCURRENCE_PRUNING_20261105.json`。

### 私有两状态逆向循环裁剪（2026-11-05）

`initial_goal_projection_v2` / `initial_goal_repeat_proof_v4` 在上述范围分析收敛后，识别纯粹的 `q → p` / `p → q` 转移对。无需业务标签或名称：使用解析后的稳定状态 ID、全部输出、转移和删除效果，包括旧格式隐式覆盖。

仅当以下条件全部满足才排除逆向活动：q 初始为真且 p 初始为假；两项活动各只有一个输出并仅删除其转移输入；范围内其他活动不能写入这两个状态，也不能依赖 q；本次正目标不要求 q、负目标不禁止 p；无外部状态变化。发现器用索引提出证书，独立检查器直接扫描解析后的活动重新核验。完整批次核验失败或超时时，不应用该批删除，保留之前已证明安全的范围。

证明是任意方案的删除投影：保留第一次正向执行的原始时间，删除所有逆向执行和后续正向执行。p 只会保持更久，q 的外部使用已排除；最终正负目标不受影响。其余时间、首次执行身份不变，资源容量及区间锁只会放松。因此投影保留可行性，工期和执行次数均不增加。再运行原有范围分析；失去逆向生产者的 q 成为不可再生的转移输入，正向活动最多创建一个实例。这是原有有限执行边界内的最优性保持，不是给所有循环强加一次上限。

拆后维修、额外状态效果、其他活动消耗/破坏安装状态、最终要求拆卸等均阻止应用此规则。证明不了就保留原来的重复能力。诊断位于 `stats.model.occurrence_pruning.scope_analysis.inverse_cycle_proofs`，包括正向/逆向活动 ID、初始/持久状态 ID、核验结果与轮次；逐活动排除原因是 `unnecessary_inverse_reset`。原始快照、哈希、项目配置和回放场景不变。

验证包含独立穷举、与关闭裁剪的 CP-SAT 对照、维修/换件恢复、物料释放、首次/项目时间窗、午休、夜班、独占、证书篡改及超时回退。219 项相关回归及 1 项混合循环补充测试通过。5/10/15/20 对两类场景的复测记录见 `docs/validation/INVERSE_CYCLE_PRUNING_20261105.json`。规模测试统一每活动最多执行 3 次（包含首次）、单线程、种子 11、60 秒；此测试设置不改变系统自动上限策略。

## 必做活动识别（2026-11-06）

当前默认关闭此项增强（`_MANDATORY_ENCODING = 'none'`），因果层级同样默认关闭。
下面保留识别规则及历史实验说明；仅在独立对照进程显式选择 `appended` / `early` 时应用。
关闭后不运行必做识别器、不添加强制存在等式、不固定首次存在变量；业务前置条件仍正常生效。

`app/core/joint_mandatory.py` 在现有范围和实例裁剪之后，根据当次输入增加必要的执行选择约束。只采用三条规则：初始缺失的正目标需要生产者；初始存在的终态禁止状态需要净删除者；已经证明必做的活动，其初始缺失前置状态需要生产者。仅有一个可用活动定义能提供该状态变化时，证明其至少执行一次；存在替代活动则不强选。转移前置同样处理，额外输出和净删除沿用解析后的业务语义。状态变化事件保守跳过。

编译器仅添加 `mandatory:<activity_id>` 命名的首实例 `present == 1`。既有实例前缀约束使它等价于至少执行一次，不限制重复次数，不固定开始时间或活动顺序。初始已成立的正状态不做失效推导，也不增加恢复顺序、工期/执行次数界限、提示或搜索参数；原有日历、资源、窗口、独占、回放及两阶段目标不变。诊断在 `stats.model.mandatory_activities`，包含逐活动证明理由与新增约束数量。

## 约束与边界

支持当前共享场景的串行/并行、不可抢占、正目标和最终负目标、前置保留、转移消耗、独立删除、额外输出、状态恢复循环、容量汇总资源、释放事件及硬活动时间窗口。资源不分配到具体人员/设备实例。负目标是最终状态不含该事实，不是全过程禁止该事实出现。

时间窗口通过场景 JSON 导入或 `PATCH /api/v1/planner-scenarios/{id}` 的 `time_windows` 字段维护；本次不增加 Excel 列或独立图形编辑器。每个活动最多一个窗口，约束该活动的每次实际执行，未选中的活动不因此变成必做任务：

```json
{
  "time_windows": [
    {"id": "window-1", "activity_id": "<活动ID>", "earliest_start": 120, "latest_finish": 180}
  ]
}
```

窗口表示开始时间不早于 `earliest_start`、完成时间不晚于 `latest_finish`，时间与场景 `start_time` 使用同一整数坐标，界面按分钟展示。导入重建活动 ID 时同步重映射窗口引用；作用域排除的活动不参与窗口编译。含窗口的场景应使用 JSON 交换；现有 Excel 契约未扩展。原三引擎遇到非空窗口返回 `UNSUPPORTED`，避免静默忽略新增约束。

外部事件直接增删状态、工作日历、调度规则、计划调整、资源实例目前未接入联合模型，已知非空配置会明确返回 `UNSUPPORTED`。当前状态必须是共享场景中的静止状态快照，不支持从正在执行的活动中途续算；不要把它理解为旧计划调整中心全部能力已经迁移。

## 运行级首次执行时间窗

`POST /api/v1/planner-runs` 和 `/async` 接受可选 `activity_time_windows`，默认空数组：

```json
{
  "display_start_at": "2026-11-05T08:00:00+08:00",
  "display_timezone": "Asia/Shanghai",
  "activity_time_windows": [
    {"activity_id": "<活动ID>", "earliest_start_at": "2026-11-05T08:10:00+08:00", "latest_finish_at": "2026-11-05T08:15:00+08:00"}
  ]
}
```

两个日期分别可为null或省略；都为空不产生约束。非空日期须带时区、精确到分钟，完成上限不得早于开始下限。同一活动只能绑定一行，且必须存在于本次有效范围。活动未被选中时不受窗口强制；不能满足窗口的必要活动由求解器给出无解，不伪装为输入格式错误。

入队时按 `start_time + (日期 - display_start_at)` 换算自然分钟，保存在有效快照的 `run_time_windows` 中并纳入hash，原始日期在运行请求中保留。只对首次执行应用完成上限；开始下限通过释放事件同时保证模型和回放一致（后续执行本来就在首次之后）。最终回放按实际执行顺序检查首次开始/完成，活动暂停期间也计入真实完成时间。提前排程不会越过释放下限。早于计划开始的开始下限自然满足，完成上限早于计划开始则禁止选择该活动。

旧 `time_windows` 的双端整数分钟和全部执行语义不变；旧规则与新规则同时生效。其他引擎返回UNSUPPORTED。能力字段 `run_activity_time_windows_supported`、`run_activity_time_windows_scope=first_occurrence`、`run_activity_time_windows_optional_bounds` 用于前端识别。历史缺失新字段按空数组处理，重试幂等校验包含新参数。

## 必做信息的提前编译实验

求解结果提取、执行次数优化、反馈认证仍读取具名存在变量，因此无需改变回放或前端契约。

当前默认改为 `none`，保留 `appended` / `early` 供独立对照；不自动按项目或名称选择模式。

## 执行实例因果层级实验

`joint_cpsat._CAUSAL_RANKS` 是独立的内部编译开关，默认关闭，不是场景输入字段。
开启时，在原模型变量之后为每个实例增加 `causal_rank`，范围为
`0..min(max_steps, 实例槽位数)`；选中实例至少为 1，未选实例的层级在域内自由取值。
当前策略为 `conditional_support_dag_v2_unbound_absent`，已取消旧版“未执行则层级等于 0”的辅助绑定。
是否执行仍完全由实例的 `present` 变量决定，不从层级值推断。
只有当现有支持选择变量选中了“生产实例 → 使用实例”时，才要求生产者层级小于使用者层级。
初始事实没有生产实例，终态目标没有使用实例，因此不额外创建对应节点。
不增加 AllDifferent、时间先后、资源排序或目标函数；原支持选项、重复上限、破坏保护与时间约束全部保留。

正确性依据：原支持约束要求 `producer.end <= consumer.start`，活动时长严格为正，
所以任何合法方案的实例支持图都是 DAG。对选中的实例作拓扑编号，最大层级不超过执行次数，
即可扩展为新模型的解；去掉层级变量又能恢复原模型的解。因此保持原排程可行域及两阶段最优值。
同一活动的不同实例是不同节点，允许“安装① → 拆卸① → 安装②”；独立并行活动可以共享层级。
这只加强支持图的无环性，不为资源冲突或状态破坏保护另设层级边。

专项测试包含小模型全部投影排程的等价性、原变量/约束/目标不变、仅靠层级约束拒绝错误闭环、
真实恢复序列、并行同层级、三次上电与首次执行时间窗。
`scripts/benchmark_causal_ranks.py` 固定现有 `appended` 必做编码和默认传播，只比较层级开关；
8 场景使用种子 11，正常安装、物料晚到、当前维修恢复追加种子 23、37，共 28 次独立求解。

原有最优工期及该工期下最少执行次数，所有返回方案通过回放；历史 00:42 维修输入开关两组

## 状态、证据与规范化

结果区和 API 区分 `OPTIMAL`、`INFEASIBLE`、`TIMEOUT_PARTIAL`、`TIMEOUT_EMPTY`、`FEASIBLE`、`UNKNOWN`、`UNSUPPORTED`、`ERROR`。超时不等于无解。返回 `proven_optimal`、`proven_infeasible`、`lower_bound`、`first_solution_seconds` 和搜索分支/冲突等统计，工期与执行次数均证明最优时返回 OPTIMAL。两项目标共用同一预算。工期已经证明最优而次数尚未证明时，返回 TIMEOUT_PARTIAL 并保留已校验的方案。stats.makespan_proven_optimal 与 stats.execution_count_proven_optimal 分别记录两项证明，lower_bound 始终以工期分钟表示。

规范化先保持所有原有不重叠区间的先后关系，把活动提前至合法的释放/前驱边界，再在所有正负目标满足且无在途活动时停止，省去目标之后的尾部动作。共享 Simulator / Validator 回放，加上独立资源区间扫描和窗口检查，保证交付方案有效；任何校验错误都不能继续保留最优证明标识。

`stats.normalization` 分开记录原始区间真实工期、提前执行节省和目标达成后截尾节省。CP-SAT 的 `finish` 变量可能有松弛，不能把其原始目标值与区间真实工期的差都算成规范化收益。界面「求解指标」展示下界及这些分项。
