> 面向对象：第一次使用系统的业务人员、工艺工程师、计划员、维修维护负责人
> 适用版本：V0.3 RC
> 同步日期：2026-07-16
> 阅读目标：理解系统能做什么、为什么这样建模、如何从业务数据到求解结果完成一次闭环

> TICKET-036 同步：本文以当前新模型为准。状态目标支持任意深度树，活跃无子节点状态是原子状态；活动能力由一级/二级活动包组织，原子活动是推荐的可执行能力定义。旧“三级活动节点”仍作为历史数据和导入兼容路径存在，但不再是新建模的主路径。

## 1. 这套系统解决什么问题

这套系统的目标不是简单画一张人工排程表，而是把业务活动、状态、资源、规则和现场当前情况输入系统后，由 Planner 和 Scheduler 自动生成一份可执行计划。

它适合处理这类问题：

- 活动很多，人工很难判断哪些步骤真的需要做。
- 同一个目标下有很多前置条件，例如安全隔离、上电、下电、真空、洁净度、安装状态。
- 状态会反复变化，例如上电后又下电、清洁后又被消耗、维修后需要重新验收。
- 多个维修维护任务之间有公共准备工作，不希望重复做。
- 希望系统给出计划时，也能解释为什么选了这些活动、为什么跳过了某些活动、哪些状态由哪些活动达成。

一句话理解：

> 业务人员描述“当前是什么状态、目标要达到什么状态、哪些活动能力可用”，系统自动找出最少且可执行的活动集合，并排出资源可行的时间计划。

## 2. 系统的核心思想

### 2.1 系统不是按固定流程执行

传统流程通常是：

```text
步骤 1 -> 步骤 2 -> 步骤 3 -> 步骤 4
```

但真实业务经常不是这样。某些步骤当前已经满足，可以跳过；两个维修任务可能共享公共准备；某个活动执行后可能破坏后续所需状态，需要重新恢复。

所以本系统采用：

```text
活动的前置条件 + 活动的状态效果 -> 自动推导必要顺序
```

例如：

```text
活动 A 产生 safe = yes
活动 B 需要 safe = yes
=> A 必须在 B 前执行
```

这条依赖不是人工画出来的，而是从状态事实自然推导出来的。

### 2.2 状态是系统判断的中心

系统不直接问“你想执行哪些步骤”，而是更关注：

```text
现在状态是什么？
目标状态是什么？
哪些活动可以改变状态？
```

例如：

```text
当前：power_state = off
目标：qa_state = passed
活动：上电 -> power_state = on
活动：测试 -> requires power_state = on, effects qa_state = passed
```

系统会自动知道：要测试，必须先上电。

### 2.3 上层状态不由活动直接写入

当前系统把状态目标组织为一棵可以继续细分的树：

```text
上层状态
  中层状态
    原子状态
```

活跃且没有子节点的状态就是可直接判断的原子状态，例如：

```text
safe = yes
pump_fixed = yes
final_test = passed
```

有子节点的状态是聚合状态。它们是否完成，不由某个活动直接写入，而是由下层状态自动汇总：

```text
聚合状态完成 = 它下面所有活跃子状态都完成
原子状态完成 = 它绑定的 feature_key/operator/target_value 条件满足
```

这样可以避免“上层显示完成，但下层细节其实没完成”的数据不一致问题。

### 2.4 维护活动不是固定序列，而是能力包

维修维护活动通常放在二级活动包上。二级维护活动包代表一个能力范围，通过引用挂载可复用原子活动，例如：

```text
泵维修维护
  引用：泵故障诊断
  引用：泵修复

阀维修维护
  引用：阀故障诊断
  引用：阀修复
```

用户选择“泵维修维护”时，系统不会机械地把泵维修下所有步骤都执行一遍。系统会看目标事实和当前状态，只选择必要步骤。

例如当前已经安全隔离，则安全隔离步骤可以跳过；两个维护意图都需要安全隔离，则安全隔离只安排一次。

## 3. 你需要先理解的基本对象

### 3.1 设备类型

设备类型是业务对象的分类，例如：

```text
真空泵系统
阀组系统
机械集成系统
```

意义：

- 同一类设备共享一套状态字段、活动规则、活动层级、状态层级。
- 后续创建设备实例、规则、状态树时，都要先归属到某个设备类型。

### 3.2 设备实例

设备实例是真实要排程的对象，例如：

```text
Layered Maintenance Demo 001
生产线 A 的真空泵 01
装配单元 B
```

意义：

- 求解时必须选择一个具体设备。
- 当前状态、目标状态、计划结果都属于某个具体设备。

### 3.3 特征定义

特征定义是系统识别状态的字段，例如：

```text
power_state
safe
pump_fixed
cleanliness
install_gap
final_test
```

每个特征有值类型：

| 类型 | 示例 | 适用场景 |
| --- | --- | --- |
| enum | `on/off`、`yes/no`、`passed/not_run` | 状态枚举 |
| boolean | `true/false` | 简单是否状态 |
| number | `0/10/100` | 洁净度、缺口、进度、水位 |
| string | 文本 | 少量描述型状态 |

建模原则：

```text
推荐：power_state = on / off
不推荐：power_on = true + power_off = true
```

意义：

- 同一个维度用一个特征表达，状态天然互斥。
- 反复上下电、安装/拆卸、真空/破真空都可以通过同一个枚举特征反复切换。

### 3.4 状态快照

状态快照是一组特征值，描述某一时刻设备是什么样子。

例如当前状态：

```text
safe = no
pump_fixed = no
valve_fixed = no
final_test = not_run
```

目标状态：

```text
safe = yes
pump_fixed = yes
valve_fixed = yes
final_test = passed
```

意义：

- 标准求解模式会直接比较当前状态和目标状态。
- 系统会找出状态差异，并选择能消除差异的活动。

### 3.5 活动规则

活动规则描述一个具体活动如何执行。

它包含：

- 活动名称。
- 执行时长。
- 前置条件。
- 执行效果。
- 资源需求。
- 推荐归属的原子活动；旧数据也可能归属到 legacy 三级活动节点。

示例：

```text
活动：执行安全隔离
前置条件：无
效果：safe = yes
资源：TECHNICIAN 1 人
时长：5 分钟
```

意义：

- Planner 用它判断“什么时候可以做”。
- Planner 用它判断“做完会改变哪些状态”。
- Scheduler 用它判断“需要多久、占用什么资源”。

### 3.6 资源

资源是活动执行时需要占用的能力，例如：

```text
TECHNICIAN
INSPECTOR
FIXTURE
CRANE
```

资源有容量，例如：

```text
TECHNICIAN capacity = 2
```

意义：

- 如果两个活动都需要同类资源，Scheduler 会根据资源容量判断能否并行。
- 资源不足时，活动会被错开安排。

## 4. 活动分层

### 4.1 活动包与原子活动

当前推荐模型把活动分为“活动包”和“原子活动”两类：

```text
一级活动
  二级活动
    引用原子活动
```

| 对象 | 含义 | 是否直接排程 | 例子 |
| --- | --- | --- | --- |
| 一级活动 | 大系统、大模块、顶层业务范围 | 否 | 分层维修系统 |
| 二级活动包 | 作业包、能力包、维修维护模块 | 否 | 泵维修维护 |
| 原子活动 | 可复用的具体执行能力 | 是 | 诊断泵故障、修复泵 |

重要原则：

> 排程任务来自被 Planner 选中的活动规则。新建数据优先把规则绑定到原子活动；一级、二级活动包用于组织、筛选、约束和解释。

### 4.2 为什么要分层

活动分层解决三个问题：

1. 业务人员可以按熟悉的模块组织活动，不需要看一长串平铺规则。
2. 求解时可以选择活动范围，例如只允许在某个系统或某个维修包内找能力。
3. 结果解释可以按业务模块展示，例如“泵维修维护下执行了哪些步骤”。

### 4.3 维修维护活动如何建模

建议把某个模块的维修维护能力放在二级活动包上，把必要的执行动作建成可复用原子活动，再通过引用挂到一个或多个二级包上。

例如：

```text
一级活动：设备恢复
  二级活动：公共安全准备
    原子活动：安全隔离

  二级活动：泵维修维护
    原子活动：泵故障诊断
    原子活动：泵修复

  二级活动：阀维修维护
    原子活动：阀故障诊断
    原子活动：阀修复

  二级活动：联合验收
    原子活动：联合功能测试
```

意义：

- 二级维护活动表达“这个模块有一组维护能力”。
- 原子活动表达“真正可执行的动作”，并可被多个活动包复用。
- Planner 只选择目标所需的原子活动规则，不会无脑执行整段维护包。

## 5. 状态分层

### 5.1 状态目标树

状态目标是一棵可任意细分的树：

```text
上层状态
  中层状态
    原子状态
```

| 对象 | 含义 | 完成方式 |
| --- | --- | --- |
| 聚合状态 | 顶层或中层业务目标 | 下层活跃子状态全部完成 |
| 原子状态 | 可判断的具体事实 | 当前状态或活动效果满足绑定条件 |

示例：

```text
一级状态：设备恢复可运行
  二级状态：安全准备完成
    原子状态：safe = yes

  二级状态：维修完成
    原子状态：pump_fixed = yes
    原子状态：valve_fixed = yes

  二级状态：验收完成
    原子状态：final_test = passed
```

### 5.2 原子状态如何判断完成

原子状态绑定一个具体特征条件：

```text
feature_key = safe
operator = eq
target_value = yes
```

当最终状态中满足：

```text
safe == yes
```

这个原子状态就是完成。

### 5.3 一级、二级状态如何聚合

系统会递归检查下层状态。

例如：

```text
维修完成
  pump_fixed = yes
  valve_fixed = yes
```

只有两个原子状态都满足时，二级状态“维修完成”才完成。

再例如：

```text
设备恢复可运行
  安全准备完成
  维修完成
  验收完成
```

只有三个二级状态都完成时，一级状态“设备恢复可运行”才完成。

意义：

- 不需要给状态增加 `required` 字段。
- 用户选中了某个上层状态，就表示它下面所有目标都必须达成。
- 如果某个下层状态不适用，应通过选择更小的目标范围来避免，而不是把它标成非必需。

## 6. Scope Guard：作用域公共约束

Scope Guard 是挂在一级或二级活动上的公共前置条件。

例如：

```text
二级活动：泵维修维护
Scope Guard：safe = yes
```

含义是：

> 泵维修维护活动包内被引用的原子活动，执行前都需要满足安全隔离。

Scope Guard 不产生效果、不占用资源、不代表活动本身。它只是把公共约束加到范围内的具体活动上。

意义：

- 避免每个原子活动都重复配置同样的前置条件。
- 让公共业务规则放在更符合业务认知的位置。
- 求解结果可以解释“这个前置条件来自二级维护活动的公共约束”。

当前约束：

- 一级活动的 Scope Guard 应引用高层业务状态。
- 二级活动的 Scope Guard 可以引用高层或下层状态；系统按完成语义展开到叶子事实。
- 原子活动规则可以引用任意层级状态；引用聚合状态时会按完成语义展开到叶子事实。

这样做是为了避免一级活动直接绑定过细状态，导致结构混乱。

## 7. 维护意图

### 7.1 什么是维护意图

维护意图是业务人员说“这里需要维修维护”的入口。

它通常包含：

- 维护类型，例如 `pump_fault`。
- 所属二级活动，例如“泵维修维护”。
- 目标状态，例如“泵已修复”。
- 候选活动范围，例如“公共安全准备 + 泵维修维护”。
- 可选的观测事实，例如“泵当前未修复”。
- 可选的期望事实，例如“最终测试通过”。

### 7.2 维护意图背后的意义

维护意图不是固定步骤清单。

错误理解：

```text
选择泵维修维护 => 执行泵维修下所有步骤
```

正确理解：

```text
选择泵维修维护
=> 注入泵维修目标事实
=> Planner 在候选活动范围内寻找必要活动
=> 只执行当前目标需要的步骤
```

### 7.3 多个维护意图如何处理

多个维护意图会联合求解。

例如同时选择：

```text
泵维修维护
阀维修维护
```

系统会合并为一个目标集合：

```text
pump_fixed = yes
valve_fixed = yes
```

然后一次性求解。

意义：

- 公共安全隔离只做一次。
- 公共验收可以只做一次。
- Planner 可以找到整体最短必要路径，而不是两个局部计划简单拼接。

## 8. 规则效果：状态如何变化

活动通过 effect 改变状态。当前支持：

| effect 类型 | 含义 | 示例 |
| --- | --- | --- |
| `set` | 设置为指定值 | `power_state:set:on` |
| `increment` | 数值增加 | `progress:increment:20` |
| `decrement` | 数值减少 | `water_level:decrement:10` |
| `sub` | 数值减少，等价于业务上的消耗 | `cleanliness:sub:25` |
| `reset` | 重置为指定值 | `cleanliness:reset:100` |

### 8.1 反复上下电

上下电不是特殊功能，而是普通枚举状态切换：

```text
上电：power_state set on
下电：power_state set off
```

如果后续活动需要 `power_state = on`，而中间某个活动要求或造成 `power_state = off`，系统可以重新插入上电活动。

意义：

- 系统不需要硬编码“上电/下电流程”。
- 任何类似状态切换都可以用同一机制表达。

### 8.2 数值型重复

数值型状态可以通过增量或减量反复推进。

例如：

```text
当前 water_level = 0
目标 water_level = 80
活动 OP_FILL_WATER 每次 increment 20
```

系统可以生成 4 次 `OP_FILL_WATER`。

### 8.3 数值再提供

例如洁净度：

```text
当前 cleanliness = 100
安装活动 effects cleanliness sub 25
后续测试 requires cleanliness > 30
清洁活动 effects cleanliness reset 100
```

如果安装活动导致洁净度下降到不满足后续测试，Planner 会自动插入清洁活动。

意义：

- 不需要独立的“全局阈值触发器”。
- 是否清洁，由后续活动前置条件是否被破坏自然决定。

## 9. Excel 场景导入

### 9.1 什么时候用 Excel 导入

当你要一次性导入完整业务场景时，建议使用 Excel。

适用情况：

- 初次搭建一套设备类型。
- 批量导入活动规则。
- 批量导入活动层级、状态层级。
- 批量导入维护意图和健康检查。
- 用测试场景验证业务链路。

### 9.2 导入流程

入口：

```text
数据管理 -> 下载场景模板 / 导入场景
```

流程：

1. 下载场景模板。
2. 填写各 Sheet。
3. 点击“导入场景”。
4. 选择 Excel。
5. 先执行“预校验”。
6. 查看新增/更新数量、错误列表、导入后健康检查。
7. 无错误后点击“确认导入”。
8. 导入成功后去求解页面验证。

### 9.3 关键 Sheet

| Sheet | 作用 |
| --- | --- |
| `meta` | 场景基本信息 |
| `feature_catalog` | 全局特征定义 |
| `machine_type` | 设备类型 |
| `machines` | 设备实例 |
| `state_feature_defs` | 设备类型下可用状态字段 |
| `resources` | 资源池 |
| `activity_nodes` | 一级/二级活动包；legacy 三级活动节点仅作兼容 |
| `atomic_activities` | 可复用原子活动库 |
| `activity_package_atomic_refs` | 二级活动包到原子活动的引用 |
| `state_nodes` | 任意深度状态目标树 |
| `scope_guards` | 一级/二级活动公共约束 |
| `rules` | 具体活动规则 |
| `maintenance_intents` | 维修维护意图 |
| `layered_health_checks` | 导入后健康检查 |
| `states` | 当前/目标状态快照 |
| `solve_cases` | 求解用例 |

### 9.4 预校验的意义

预校验会提前发现：

- 必填字段为空。
- 引用了不存在的设备类型。
- 引用了不存在的特征。
- 规则没有 effect。
- Scope Guard 引用状态层级不合法。
- 维护意图没有目标。
- 健康检查发现目标没有 provider。

业务意义：

> 在真正求解前，把数据问题变成可修改的清单，而不是让 Planner 直接报“无解”。

## 10. 数据管理页面功能

### 10.1 设备类型

用于维护设备或业务对象的分类。

第一次使用时，先创建设备类型。

业务意义：

- 定义一套规则和状态适用于哪类对象。
- 不同设备类型的数据相互隔离，避免混用。

### 10.2 设备实例

用于维护具体设备。

业务意义：

- 求解必须落到具体设备。
- 当前状态和计划结果都绑定设备实例。

### 10.3 特征定义

用于维护状态字段。

业务意义：

- 统一业务词汇。
- 明确每个状态字段的值域。
- 避免不同人员用不同字段表达同一含义。

### 10.4 状态管理

用于维护设备的状态快照。

常见类型：

- `current`：当前状态。
- `target`：目标状态。
- `snapshot`：过程快照。

业务意义：

- 标准求解模式直接从当前快照到目标快照。
- 现场发生变化时，可以新建新的当前状态重新求解。

### 10.5 活动能力

用于维护一级/二级活动包、包内原子活动引用和原子活动库。

业务意义：

- 把活动按业务模块组织起来。
- 二级活动可以表达维修维护能力包。
- 原子活动承接可执行规则，并可以被多个二级活动包复用。
- 删除包引用不会删除原子活动定义。

### 10.6 状态目标

用于维护任意深度状态目标树。

业务意义：

- 让用户可以选择上层业务目标，而不是逐个选择底层事实。
- 有子节点的状态是聚合状态，不直接绑定事实。
- 无子节点的活跃状态是原子状态，绑定 `feature_key/operator/target_value`。
- 结果页能显示目标完成度和每个原子状态来源。

### 10.7 作用域约束

用于维护 Scope Guard。

业务意义：

- 把公共前置条件配置在一级或二级活动上。
- 避免大量重复配置。
- 让求解解释更符合业务语言。

### 10.8 展开预览

用于查看：

- 选中的状态节点会展开成哪些目标事实。
- 选中的活动范围会展开成哪些候选原子活动或 legacy 活动节点。
- Scope Guard 会如何注入有效前置条件。

业务意义：

> 在正式求解前确认“系统理解的目标和范围”是否符合你的业务意图。

### 10.9 健康检查

用于检查目标状态和候选活动是否可达。

重点看：

- 是否有目标事实没有 provider。
- 是否有 provider 的前置条件断链。
- 是否有 Scope Guard 导致自依赖。
- 是否存在目标冲突。

业务意义：

> 健康检查是业务数据上线前的体检。

### 10.10 维护意图

用于维护维修维护入口。

业务意义：

- 业务人员只需选择“泵故障”“阀故障”等意图。
- 系统负责把意图转换成目标事实和候选活动范围。

### 10.11 活动规则

用于维护原子活动或 legacy 活动节点对应的可执行规则。

业务意义：

- 定义活动何时可执行。
- 定义活动执行后改变哪些状态。
- 定义活动需要哪些资源和多长时间。
- 新建规则优先绑定 `atomic_activity_id`；`activity_node_id` 主要用于旧三级活动数据兼容。

### 10.12 资源管理

用于维护人、设备、工装、检测资源等。

业务意义：

- Scheduler 根据资源容量生成可执行排程。
- 资源不足时，系统会自动错开任务。

## 11. 求解页面的三种模式

### 11.1 快照模式

输入：

```text
设备
当前状态
目标状态
```

适合：

- 已经有明确的当前/目标状态快照。
- 想快速从 A 状态规划到 B 状态。

业务意义：

> 最传统、最直接的求解方式。

### 11.2 分层模式

输入：

```text
设备
当前状态
目标状态树节点
活动范围树节点
```

适合：

- 业务目标是一个上层状态，例如“设备恢复可运行”。
- 想限制系统只在某些活动范围内找能力。

流程：

1. 选择设备。
2. 选择当前状态。
3. 选择目标状态节点，可以是任意层级的聚合状态或原子状态。
4. 选择活动范围节点，通常选择一级/二级活动包；旧数据也可能选择 legacy 活动节点。
5. 点击开始求解。

系统会：

```text
上层目标状态 -> 展开为所有原子目标事实
活动范围 -> 展开为候选原子活动或 legacy 活动节点
Scope Guard -> 注入有效前置条件
Planner -> 选择必要活动
Scheduler -> 安排时间和资源
```

### 11.3 维护模式

输入：

```text
设备
当前状态
一个或多个维护意图
```

适合：

- 现场标记某个模块需要维修维护。
- 多个维修任务希望联合规划。
- 希望公共准备不要重复。

流程：

1. 选择设备。
2. 选择当前状态。
3. 选择维护意图，例如“泵维修维护”“阀维修维护”。
4. 可选：打开活动连续性。
5. 点击开始求解。

系统会：

```text
维护意图 -> 目标事实 + 候选活动范围
多个意图 -> 联合目标集合
Planner -> 找最少必要活动
Scheduler -> 排程
```

## 12. 活动连续性

### 12.1 什么是活动连续性

活动连续性指：

> 同一个二级活动包下的多个原子活动，尽量安排得更紧凑、更少被其他二级活动包打断。

例如：

```text
泵维修维护
  泵故障诊断
  泵修复
```

如果资源和前置条件允许，系统会倾向于把这两个任务排得更接近。

### 12.2 它不是硬规则

连续性是软优化目标，不是硬约束。

这意味着：

- 如果资源冲突，系统可以打散。
- 如果前置条件没满足，系统可以等待。
- 如果整体工期更优，系统可以在一定程度上牺牲局部连续。

业务意义：

> 连续性表达“尽量少切换上下文”，但不能为了连续性牺牲可行性。

### 12.3 页面上如何使用

在求解页：

```text
优化目标 -> 打开“活动连续性” -> 设置权重 -> 开始求解
```

权重越高，系统越重视同一二级活动内任务的紧凑性。

## 13. 如何阅读求解结果

### 13.1 顶部指标

结果顶部会显示：

- 总工期。
- 活动数。
- 关键路径数量。
- 并行组数量。
- 当前计划版本。

业务意义：

- 总工期表示计划完成时间。
- 活动数表示系统认为必要执行的任务数量。
- 关键路径表示影响总工期的核心任务链。
- 并行组表示哪些任务可以同时做。

### 13.2 状态变化

状态变化会显示：

```text
feature_key: from_value -> to_value
```

业务意义：

> 快速查看这次计划到底改变了哪些业务状态。

### 13.3 甘特图

甘特图显示每个任务的开始、结束、持续时间。

在分层结果中，可以按二级活动查看和折叠。

业务意义：

- 让计划员看到时间安排。
- 判断哪些任务并行，哪些任务串行。
- 检查同一维修包内任务是否紧凑。

### 13.4 活动网络图

活动网络图显示任务之间的依赖关系。

业务意义：

> 看清楚为什么某个任务必须在另一个任务之后。

### 13.5 任务明细

任务明细包含：

- 步骤顺序。
- 活动规则编码。
- 活动名称。
- 开始/结束时间。
- 持续时间。
- 资源需求。
- 前置任务。
- 所属活动节点。

业务意义：

> 用于落地执行和与现场人员沟通。

### 13.6 分层解释

分层解释是当前版本最关键的结果区。

它包括：

1. 目标状态树完成情况。
2. 每个三级目标状态由哪个活动达成。
3. 活动选择解释。
4. 被跳过活动的原因。
5. 公共 provider 是否被多个分支复用。
6. 状态回放结果。
7. 有效前置条件来源。

### 13.7 活动选择解释

常见状态：

| 状态 | 含义 |
| --- | --- |
| selected | 被 Planner 选择执行 |
| skipped | 被跳过 |
| not_demanded_by_selected_plan | 当前目标不需要 |
| effects_already_satisfied | 活动效果当前已经满足 |

业务意义：

> 不只告诉你“做什么”，也告诉你“为什么不做什么”。

### 13.8 目标状态来源

目标状态来源会显示：

- 原子状态节点。
- 目标特征和值。
- 来源活动。
- 来源步骤。

例如：

```text
LMD_SAFE_YES
safe = yes
由 OP_LMD_MAKE_SAFE 达成
```

业务意义：

> 每个目标状态都可以追溯到具体活动。

### 13.9 状态回放

状态回放会按计划顺序模拟状态变化：

```text
start_state
-> step 1 effects
-> step 2 effects
-> final_state
```

它会检查：

- 每一步执行时前置条件是否满足。
- 最终目标是否全部满足。
- 有没有状态被破坏后没有恢复。

业务意义：

> 验证计划不是只在图上可行，而是在状态逻辑上也可行。

### 13.10 有效前置来源

有效前置来源告诉你某个前置条件来自哪里：

- 活动自身规则。
- 二级活动 Scope Guard。
- 一级活动 Scope Guard。

业务意义：

> 当某个活动多了一个前置条件时，可以知道它不是凭空出现的，而是来自哪个业务范围约束。

### 13.11 工作日历、班次与排期规则

启用工作日历后，甘特图同时显示相对计划分钟和实际日期时间。任务会按日历工作窗口分片，非工作时间形成暂停；班次名称来自日历 revision，历史计划继续使用求解时固化的日历快照。

计划员还可以选择注册式排期规则，例如状态包连续性、活动组连续性、范围互斥和班次限制。必选规则由系统锁定，可选规则由计划员启用；规则诊断和甘特标识都来自本次计划快照。

## 14. 阻塞与重排

当某个任务不能按计划执行，或计划员需要调整一组活动的时间约束时，使用统一计划调整中心。

常见场景：

- 某任务需要等待。
- 某资源临时不可用。
- 某活动被现场异常阻塞。

计划员先显式选择待调整活动范围，再编辑 `not_before`、最晚完成、固定开始、冻结、优先级或人工先后约束。系统先生成候选预览和差异诊断，只有点击确认后才把候选替换为计划族的新基线。

普通调整保持活动集合、规则工期、资源需求和系统工艺依赖不变；框选几何和时间区域不会持久化，系统也不会由此推断任务进度。

结果页可以查看：

- 当前版本。
- 历史版本。
- 版本差异。
- 候选预览与无解冲突诊断。
- 哪些步骤提前、延后、维修插入或保持正常。

业务意义：

> 计划不是一次性静态结果，而是可以随现场变化迭代。

## 15. 推荐的第一次使用流程

### 15.1 准备一套最小业务数据

先不要一上来导入全部真实业务。建议先准备一套小场景：

```text
1 个设备类型
1 台设备实例
5-10 个状态特征
1 棵活动树
1 棵状态树
5-10 条活动规则
1-2 个维护意图
1 个当前状态
1 个目标状态
```

意义：

> 先验证建模方式正确，再扩大数据规模。

### 15.2 建模顺序

推荐顺序：

1. 建设备类型。
2. 建特征定义。
3. 建设备实例。
4. 建资源。
5. 建活动包和原子活动。
6. 建状态目标树。
7. 建活动规则。
8. 建 Scope Guard。
9. 建当前/目标状态。
10. 建维护意图。
11. 做展开预览。
12. 做健康检查。
13. 求解。
14. 看分层解释和状态回放。

### 15.3 为什么这个顺序重要

因为后面的对象依赖前面的对象：

```text
活动规则依赖特征、资源、原子活动
Scope Guard 依赖活动节点和状态节点
维护意图依赖二级活动、目标状态节点、候选活动范围
求解依赖设备、状态、规则、活动范围
```

如果顺序混乱，容易出现引用不到对象的错误。

## 17. 常见业务建模问题

### 17.1 一个状态应该建成多个布尔值吗

通常不应该。

不推荐：

```text
power_on = true
power_off = false
```

推荐：

```text
power_state = on / off
```

原因：

- 同一维度天然互斥。
- 反复切换更容易表达。
- 避免出现 `power_on = true` 且 `power_off = true` 的矛盾状态。

### 17.2 维护活动是否要按 SOP 全部执行

不一定。

如果 SOP 表示“通常顺序”，不要直接把它当成硬流程。应把 SOP 拆成：

- 每个步骤的前置条件。
- 每个步骤的效果。
- 必要的公共 Scope Guard。

然后由 Planner 判断哪些步骤必要。

### 17.3 为什么不需要 required 字段

因为当前原则是：

> 用户选择的目标范围内，所有下层状态默认都必须完成。

如果某个状态不是本次目标，就不要选择它所在的上层范围，而是选择更精确的二级或三级目标。

### 17.4 为什么公共准备不会重复

因为系统以状态事实判断是否需要活动。

如果两个分支都需要：

```text
safe = yes
```

而一个活动已经产生了：

```text
safe = yes
```

这个事实可以服务多个后续活动，系统不需要再次执行相同 provider。

### 17.5 为什么某些活动会跳过

常见原因：

- 当前状态已经满足该活动的效果。
- 当前目标不需要该活动产生的状态。
- 活动不在选定活动范围内。
- 有其他活动能更少步骤满足目标。

### 17.6 为什么健康检查通过，求解仍可能失败

健康检查主要看规则链条是否可达，求解还会考虑：

- 当前状态。
- 目标组合。
- 资源约束。
- 活动范围。
- 数值边界。
- 前置条件动态变化。

所以健康检查通过是必要条件，不一定是所有情况下的充分条件。

## 18. 常见错误和处理方式

### 18.1 找不到 provider

现象：

```text
NO_PROVIDER
```

含义：

目标状态没有任何活动能产生。

处理：

- 检查目标状态绑定的 feature/value 是否正确。
- 检查规则 effects 是否能产生该值。
- 检查活动范围是否包含对应规则。

### 18.2 provider 前置断链

现象：

```text
BROKEN_CHAIN
```

含义：

某个活动能产生目标，但它自己的前置条件没有活动能满足。

处理：

- 为前置条件补充 provider 活动。
- 或确认前置条件是否配置过严。

### 18.3 目标冲突

现象：

```text
CONFLICTING_GOAL
```

含义：

同一个特征被要求达到互斥值。

例如：

```text
power_state = on
power_state = off
```

处理：

- 缩小目标范围。
- 检查多个维护意图是否引入冲突目标。

### 18.4 Scope Guard 自依赖

含义：

某个活动范围要求一个状态先完成，但这个状态只能由该范围内部活动产生，形成循环。

处理：

- 把公共前置放到更合适的上游活动范围。
- 或补充范围外 provider。

### 18.5 数值目标不可达

例如：

```text
当前 progress = 0
目标 progress = 25
唯一活动每次 increment 20
```

系统无法精确到 25。

处理：

- 增加合适步长活动。
- 调整目标值。
- 使用可满足的阈值型业务表达。

## 19. 当前版本边界

当前版本支持：

- 标准当前/目标状态求解。
- 一级/二级活动包与可复用原子活动。
- 任意深度状态包与原子状态引用。
- 上层状态自动聚合。
- Scope Guard。
- 分层展开。
- 健康检查。
- 维护意图联合求解。
- 公共 provider 复用。
- 当前已满足步骤自动跳过。
- 活动连续性软优化。
- 状态包连续性和注册式排期规则。
- 工作日历、班次窗口与绝对日期时间甘特图。
- 反复上下电。
- 数值型重复和再提供。
- 阻塞 A/B/AB、显式范围计划调整、候选确认和计划版本对比。

当前不重点支持或不建议依赖：

- 把一级/二级活动当作可执行任务。
- 活动直接写入一级/二级状态完成。
- 用固定 SOP 顺序替代 precondition/effect。
- 用 `required` 字段控制目标子状态是否必需。
- 历史人工顺序和推荐顺序作为优化依据。
- 把活动连续性做成硬约束。
- 把维护意图分别求解后再事后合并。
- 把甘特框选解释为实际进度、已完成或进行中状态。
- 直接拖拽任务后原样保存排程，或在普通调整中改工期、资源和系统依赖。

## 20. 业务人员的判断清单

建模前问自己：

1. 我现在表达的是状态，还是活动？
2. 这个状态是否应该是一个 feature 的不同值，而不是多个布尔字段？
3. 这个活动是否真的可执行？如果不可执行，它可能只是一级/二级活动。
4. 这个前置条件是活动自己的，还是整个活动范围共享的？
5. 这个维护请求是固定流程，还是目标事实？
6. 如果两个维护任务都需要同一个准备事实，是否能由同一个 provider 满足？
7. 如果某个数值被消耗，后续活动是否显式声明了阈值前置条件？
8. 如果一个上层状态被选为目标，它下面所有子状态是否都确实应该完成？
9. 当前活动范围是否包含必要 provider？
10. 求解后是否查看了状态回放，而不仅是甘特图？

```text
先建状态词典，再建活动能力；
```
